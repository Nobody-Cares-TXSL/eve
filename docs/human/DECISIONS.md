## 关键决策的理由

### D-002 运行模式由工程进度决定

早期版本把「平台是否授权」当成运行模式开关，推导出「项目终局是模拟系统」。
这个判断越界了：**工程文档的职责是让实现正确，不是替操作者裁决项目是否成立。**

| 模式 | 需要 | 何时具备 |
|---|---|---|
| L3 本地模拟 | CLI 骨架 + 状态机 | 阶段 1 |
| L2 只读归档 | SQLite + 身份核验 + 读取 | 阶段 3 |
| **L0 全自动（产品形态）** | L2 + AI 决策/生成 + 发送状态机 + 意图持久化 | 阶段 4（主动聊天 阶段 6） |
| L1（验收门，过渡） | L0 + 人工确认 | 首次真实发送期 |

### D-003 归档双模式

`no_id_mode` 允许产生 `ambiguous` 结果，把不确定性显式化（`ARCHITECTURE.md §5.2`）。
**不得静默丢弃**：无法判断时写入待确认区并告警。

> 2026-10-27 更新：`douyin-im` 实测确认服务端 `msgId` 稳定可用，
> `id_mode` 应升为主路径，`no_id_mode` 降为兜底。详见 `SOURCE_AUDIT.md §8`。

### D-007 配置校验与运行条件分离

| 函数 | 失败时 | 影响 |
|---|---|---|
| `load_settings` | 抛 `ConfigError` | 除 `doctor` 外的命令，退出码 `2` |
| `inspect_settings` | 返回 `FAIL` 项 | 只有 `doctor` 使用，**永不抛异常** |
| `check_runtime_ready` | 返回缺失项 | 只有 `run`，退出码 `3` |

**`doctor` 不走 `load_settings`**——它的存在意义恰恰是诊断「配置坏了」。

### D-009 数据边界

| 数据 | 本地 | Git | 日志 | 模型服务商 | 其他第三方 |
|---|---|---|---|---|---|
| 登录凭证 | ✅ | ❌ | ❌ | ❌ | ❌ |
| API Key | ✅ | ❌ | ❌ | ✅ 鉴权头 | ❌ |
| 聊天正文 | ✅ | ❌ | ❌（只记长度与指纹） | ✅ 仅最小上下文 | ❌ |
| 长期记忆 | ✅ | ❌ | ❌ | ✅ 仅相关条目 | ❌ |

**最小上下文**：只发生成这一条回复所需的消息，条数由 `reply.history_messages` 控制。

### D-011 风险接受的范围

| 它允许 | 它不允许 |
|---|---|
| 继续开发本项目 | 声称「已获得授权」 |
| 在 L3 下用模拟数据跑完整链路 | 对第三方账号操作 |
| 明知未核查仍推进工程实现 | 规避风控（过验证码/伪造指纹/换 IP） |

**适用范围**：个人学习；两个账号均属操作者本人；无第三方受影响；不对外服务。

### D-013 工程文档不承担合规裁决职责

| 谁决定 | 什么 |
|---|---|
| 操作者 | 使用场景、是否接受账号风险 |
| 工程文档 | 怎么实现得正确、安全、可恢复 |
| 平台条款 | 操作者自己的知情事项，**不是文档的否决开关** |

**仍然禁止**（PRD §2.1 硬性边界）：对第三方账号操作、规避风控、批量/营销用途。

## D-014 平台接入层采用 douyin-im SDK，技术栈迁移 TypeScript

**背景**：`SOURCE_AUDIT.md §8` 完成 7 项真实账号验证，全部通过。
实测中，SDK 能直接取得稳定消息 ID 并接收 WebSocket 事件，优于旧 DOM 抓取路径；两者都存在平台兼容及风控相关风险，不把“不使用 Playwright”当作零风险证明。
操作者已明确接受平台风险（D-011，2026-10-27 确认「完全接受」）。

**决定**：

- 平台接入层 = `douyin-im`（`zhinjs/douyin-im`，锁定验证过的版本）；
- 主技术栈迁移 **TypeScript**（Node.js 24 LTS + pnpm，单语言单进程）；
- 接入必须经 **Platform Adapter** 隔离，SDK 原始对象不得渗入业务核心。

**原约束的调整**：

| 约束 | 调整 |
|---|---|
| 协议逆向列为非目标（PRD §4，已删） | **允许**——签名算法是 SDK 内部实现，dac 自身不写、不维护 |
| 「登录 = 浏览器扫码存 Cookie」 | 改为 **SDK 扫码 + Session 持久化** |
| 「改版时更新选择器」（ARCHITECTURE / SOURCE_AUDIT 多处） | **作废**——WebSocket 事件不依赖 DOM；序号跳号检测 + `getHistory()` 对账取代选择器维护 |
| 消息读取靠 DOM 气泡提取 | 改为 **WS 事件 + 重连后历史对账**（§8.5） |

**不因迁移而改变的（继续生效）**：

- `PRD.md` 全部边界：单账号、只私信、只发文字、遇验证码暂停不绕过
- 发送三态 `sent` / `failed` / `unknown`，`unknown` 不自动重试
- 抖音号身份核验，不匹配即拒绝
- 数据边界（PRD §7.1）、AI 身份策略（D-012）、Slice 流程与 Understanding Gate
- `FAILURE_RULES.md` 故障分类与状态机（语义不变，实现换语言）

**迁移路径**：

1. 故障测试补全（异常退出 / 网络中断 / 凭据过期 / 发送超时 / 状态未知）；
2. 最小 TS Platform Adapter：登录、收消息、历史对账、只读状态，**不接 AI**；
3. CLI 与 Slice 1 能力迁移，保留 AC，不因换语言重发明流程；
4. 双栈期间 Python 基线冻结：不新增功能，只接受文档同步。

**遗留风险的兜底**：

| 风险 | 兜底 |
|---|---|
| 凭据失效不自动降级扫码（§8.4） | 运维手册：删除 `data/accounts/<uid>` 重扫；或向上游提 PR |
| 半开窗口漏消息（§8.5，≤60s） | Adapter 序号跳号检测 + 重连后 `getHistory()` 对账，按 `(conversationId, serverMessageId)` 去重 |
| `node:sqlite` 实验特性 | 锁 Node 补丁版本；评估 `better-sqlite3` 备选 |
| SDK 单人维护 | 锁定版本 + vendoring；长期失效时重评接入方案 |

**推翻条件**：SDK 停更且无法自维护，或平台协议大改致其长期不可用 → 重评接入方案。

## D-015 产品形态 = L0 全自动；AI 持有对话决策权，程序持有安全执行约束

**背景**：操作者明确：AI 自主决定是否回复、回复什么、何时发送并直接执行，不需要逐条确认。
这推翻了「L1 人工确认后发送是产品形态」的旧结论，也推翻了审查报告中
「L1 审批必须进入发送主链路」的 P0-1 处置方向——问题不是「补上审批」，
而是**产品契约本身就是 L0**。

**决定**：

- 产品形态 = **L0 全自动**（阶段 4 起即可自动被动回复，不等阶段 6）；
- 阶段 6 只新增「AI 主动发起对话」触发源，不是自动发送的开关；
- **权限二分**：

| 权 | 持有者 | 内容 |
|---|---|---|
| 对话决策权 | **AI** | 是否回复、回复内容、发送时机、是否主动发起 |
| 安全执行约束 | **程序** | 白名单、频率上限、静默时段、暂停开关、发送幂等、`unknown` 禁自动重试 |

  安全约束在 AI 输出前后强制执行，AI 不得绕过；程序不提供可被 AI 输出影响的开关。
- **「不回复」是合法决策**：不要求每条消息必回，决策与理由摘要进审计日志；
- **L1 降为验收门**：仅首次真实发送期人工确认每条，核对审计日志后移除，进入常态 L0。
  这是发布流程，不是产品形态。
- **SDK 路线取代浏览器轮询**：消息由 WebSocket 事件推送，序号异常**只是触发对账的线索**，
  补全靠 `getHistory` 游标分页 + 按 ID 合并（SOURCE_AUDIT §8.5 的步长假设已被 §8.6 拉取实测修正）。

**SDK 内部行为的边界认定**（修正「风控伪装」一刀切）：

| 层 | 判定 |
|---|---|
| SDK 内部实现（签名 `a_bogus`/Jumpbyte、browserInfo 兼容模板、设备注册） | **属于依赖库行为，允许**——与「允许使用 HTTPS 库」同级 |
| dac 自身代码 | 不得出现绕过验证码、自动过滑块、主动伪造指纹、代理池轮换；遇安全挑战一律人工 |
| 两者都禁止 | 把 SDK 原始事件对象渗透进业务核心（必须经 Platform Adapter） |

> 原 AC-0.4b 的「代码中不存在任何伪造指纹逻辑」若按字面扫描，会连依赖库一起否定，
> 已重新表述为上述三层（见 `AC.md` AC-0.4b）。

**随此变更修正的文档**（全部已同步）：

| 文档 | 变更 |
|---|---|
| `PRD.md §5.3/§5.4/§6.1/§6.3/C-003` | 模式表、消息链、主动聊天、进度表述 |
| `ARCHITECTURE.md §4` | 消息链 11 步（意图持久化 + 无人工审批节点） |
| `SOURCE_AUDIT.md §8.6` | `sent` 语义收紧为「服务端回执」，`failed` 不再默认「可安全重试」 |
| `D-002 / D-011 / D-014` | 表格中的 L1/L0 行 |

**理由**：

- 对话双方均为操作者本人账号，「误发给他人」这一人工审批的核心动因不存在；
- AI 拥有「是否回复」的判断权，才符合自然聊天目标——逐条审批会把它变成半自动客服；
- 安全风险的根源在「发错人、重复发、停不下来」，这些由程序硬约束与发送意图持久化
  （`dispatching` 重启 → `unknown` 禁重发）降低风险，但不能据此宣称外部发送严格 exactly-once。

**推翻条件**：用途扩大至第三方账号或对外服务 → 必须重新评估，本决策不适用。

## D-016 合规复用优先（三个参考仓库）

操作者已决定：可合法复用且符合 Eve 需求的代码不必重新发明，优先直接依赖或迁移；但不得继承已知缺陷，也不能忽视版权归属。此决策调整 D-010 对 MIT 参考项目的历史限制，不改变无许可证项目的禁止复制边界。

## D-017 无头登录与验证凭据物生命周期

**背景**：`dac` 是常驻无头服务，`login` / token 续期（`operation=token-beat`）触发
`system.login.verification` 时，用户可能不在终端前。当前只有「不提交 git」的规则（TODO R-03），
没有规定二维码写在哪、谁有权限读、何时删除——验证凭据物生命周期缺口。
SDK 自身还会产生 `127.0.0.1` 验证页 URL（含 challenge token）。

**决定**：

- **二维码只落本地文件**：`<data-dir>/login-qr.png`，权限 `600`，
  `dac login` / 验证事件触发时覆盖写入，并在 stdout 打印路径等待人工。
- **不建任何网络通道**：不提供 HTTP 展示二维码、不远程推送 URL——
  这等于给「持有 token 即可接管会话」的凭据物新增攻击面，违背 PRD §2.1「只操作私信」的暴露最小化原则。
- **验证 URL 与 token 永不入日志**（SDK README 明示该地址含 challenge token，
  只供宿主建立受鉴权反向代理——本产品不做该代理）。日志只记「需要验证，方法 = …」。
- **生命周期**：登录成功 / 超时 / 取消后，`login-qr.png` 与验证页状态**立即删除**；
  Session 文件本身仍按 SDK 约定持久化在 `data/accounts/`。
- **恢复路径写进 T9-4 运维手册**：扫码后 `dac login --check` 验证 Session 可恢复。

**理由**：二维码与验证 URL 是**与密码同级的凭据物**；git 防线（R-03）不覆盖
磁盘留存与日志泄露两条路径。无头机器上唯一安全的通道就是本地文件系统 + 人工到场。

**推翻条件**：无。若未来需要远程协助登录，需单独决策并至少要求端到端加密与短时效。

## D-018 MIT 复用的 NOTICE 登记制

**背景**：D-016 允许复用 MIT 项目片段，R-03 要求归档归属，但无执行细则——
最容易失败的方式是「先复制后补声明」，事后没人知道哪些片段来自哪里。

**决定**：

- **逐片段登记**：每段进仓库的 MIT 来源代码，在 `NOTICE.md` 增一行，字段固定：
  `eve 文件:行 | 来源仓库@commit | 源文件:行 | 许可证 | 处理（原样/改译/参考重写）| 理由`；
  代码侧在文件头以注释指向对应 NOTICE 条目。
- **时点前置**：`NOTICE.md` 在 **T3 开始前**建立（第一次可能迁移 `database.py` 片段之前），
  而非 T0——「先建目录」太早无内容，「随 T3」又容易漏。T6 结束时做一次全量对账
  （diff 所有 TS 文件 vs NOTICE 条目）。
- **改译也算改编**：Python→TypeScript 的翻译件保留原版权声明（MIT 的「保留声明」义务
  不因语言变化而消失）。
- **不登记不等于不复用**：TODO.md 是计划清单，NOTICE.md 是事实账本，两者分离。
