## D-001 技术主干选 douyin-robot，但不复制其代码

**背景**：两个参考项目都可用作起点。

**选项**：
- A. 以 `douyin-bot` 为骨架（MIT，可复制代码，功能完整）
- B. 以 `douyin-robot` 为骨架（架构清晰，但无许可证）
- C. 新写，只借鉴设计

**决定**：选 **B 的架构 + C 的实现方式**。

**理由**：
- `douyin-robot` 的分层（选择器 / 页面操作 / 决策 / 状态）更适合长期维护；
- 它按抖音号核验身份，是更安全的设计；
- 但它**没有 LICENSE**（`git ls-files` 无结果），默认版权保留，代码不可复制。

**推翻条件**：作者补充许可证，或取得书面授权。

## D-002 运行模式由工程进度决定，不由平台条款设卡

**背景**：早期版本把「平台是否授权」当成运行模式的开关，导致
`unknown` 状态下项目只能停在模拟层。这个判断越界了：
它用一个操作者不认可的合规框架，替操作者给项目判了终局。

**决定**：
- **运行模式的上限由「工程能力」决定**，不由平台条款决定；
- 阶段 1～2 用 L3（本地模拟）是因为**真实适配器还没写**，不是因为不允许；
- 阶段 3 起接入真实平台，目标是 **L1（人工确认后发送）**；
- 平台条款与风险作为**事实记录**（PRD §5.2）与**已接受的风险**（D-011）保留。

| 模式 | 需要 | 何时具备 |
|---|---|---|
| L3 本地模拟 | CLI 骨架 + 状态机 | 阶段 1 |
| L2 只读归档 | SQLite + 身份核验 + 读取 | 阶段 3 |
| **L1 半自动**（产品形态） | L2 + AI + 发送状态机 | 阶段 4 |
| L0 全自动 | L1 + 主动聊天 + 频率限制 | 阶段 6 之后 |

**理由**：
- 两个账号都属于操作者本人，无第三方受影响；
- 个人学习用途，风险由操作者承担（D-011）；
- 真正需要工程把关的是**避免事故**（发错人、重复发、停不下来），
  这些由 PRD §5.6 的工程检查项覆盖，而不是由「许可」覆盖。

**推翻条件**：使用范围扩大到第三方账号，或用于对外服务 → 需重新评估。

## D-003 阶段 2 的归档 Contract 原生支持「有 ID / 无 ID」两种模式

**背景**：两个参考项目都没有使用稳定消息 ID：
- `douyin-robot` 用纯文本 SHA256 指纹；
- `douyin-bot` 用文本滑动窗口对齐。

**决定**：
- 阶段 2 的 Contract **从一开始就定义两种模式**：`id_mode` 与 `no_id_mode`；
- 稳定 ID 是**可选输入**，不是阶段 2 的前提；
- 阶段 3 负责验证真实平台**能否**提供 ID，**不决定阶段 2 能否开始**；
- 若阶段 3 的发现需要改变 Contract，走正式设计变更记录，不在实现中悄悄改。

**理由**：
- 初版写「阶段 3 验证后若拿不到 ID，阶段 2 的 Contract 需要改写」——
  这等于说阶段 2 的成败取决于阶段 3 的结论，两个阶段互相阻塞；
- 改成原生支持两种模式后，阶段 2 可以独立开发和验收；
- `no_id_mode` 允许产生 `ambiguous` 结果，把不确定性显式化（见 ARCHITECTURE §5.2）。

**推翻条件**：无。这个设计对两种现实情况都成立。

## D-004 发送三态：sent / failed / unknown

**背景**：两个参考项目都把「点击发送」当作成功。

**决定**：引入 `unknown` 作为一等状态，**绝不自动重试**。

**理由**：
- 点击后无法确认时，重试可能导致对方收到两条；
- 宁可暂停等人工核对，也不冒重复发送的风险。

**推翻条件**：无。

## D-005 不做 Web 管理后台

**背景**：`douyin-bot` 有 FastAPI + Vue3 控制台，体验好但增加攻击面与维护成本。

**决定**：CLI 优先，不做 Web。

**理由**：
- 单人使用，CLI 足够；
- 减少常驻服务和依赖；
- 阶段 7 要求「避免引入不必要的常驻服务」。

**推翻条件**：实际使用中 CLI 操作成本明显过高。

## D-006 只支持一个目标账号

**背景**：两个参考项目都支持多好友。

**决定**：白名单只允许 1 个账号。

**理由**：
- 产品定位是「与指定账号持续交流」，不是群发工具；
- 单目标让身份核验、频率限制、记忆模型都显著简化；
- 降低误伤他人的风险。

**推翻条件**：产品定位变更（需重新评估合规性）。

## D-007 配置校验与运行条件分离

**背景**：目标账号抖音号在阶段 3 才填写，但 `doctor` 必须能在阶段 1 就跑。

**决定**：
- **配置结构校验**（字段是否存在、类型是否正确）→ 加载时失败，退出码 2；
- **运行条件校验**（目标账号是否已填、凭证是否存在）→ 只影响 `run`，不影响 `doctor` / `status` / `logs`。

**理由**：
- 否则「还没填账号」会阻止你检查 CLI 本身，形成鸡生蛋问题；
- 两类问题的修复动作不同：结构错误要改配置，条件缺失是**尚未到那一步**。

**推翻条件**：无。

## D-008 暂停状态与停止状态必须分离

**背景**：初版 AC-1.5 同时要求「pause 后 status 显示 `stopped`」和「resume 能恢复」，二者矛盾。

**决定**：引入 `pause_requested` 与 `paused_manual`，与 `stopped` 明确区分（见 ARCHITECTURE §8）。

**理由**：
- `stopped` = 进程已退出，只能 `run`；
- `paused_manual` = 进程存活，应 `resume`；
- 若两者同值，CLI 无法给出正确的下一步建议，运维时会误判。

**推翻条件**：无。

## D-009 允许将最小必要上下文发送给 DeepSeek

**背景**：PRD §7 初版写「聊天内容不上传任何第三方」，与选用云端 DeepSeek 直接冲突。
调用云端模型**必然**要把消息内容发给服务商。

**选项**：
- A. 接受发送给 DeepSeek，明确边界
- B. 改用本地推理（llama.cpp / Ollama）
- C. 取消 AI 能力

**决定**：**A**。边界见 PRD §7.1。

**理由**：
- 本地推理需要额外硬件与显著的质量/维护成本，且与本项目的核心目标（拟真对话）冲突；
- 「不上传任何第三方」这句承诺必须删掉，不能保留一个无法满足的承诺；
- 明确边界比模糊承诺更有约束力：凭证永不出本机、正文不进 git/日志、只发最小上下文。

**推翻条件**：操作者要求聊天正文也不能离开本机 → 改本地推理，需新的决策记录。

## D-010 两个参考项目都采用独立实现，不复制代码

**背景**：`douyin-bot` 是 MIT（允许复制），`douyin-robot` 无许可证（禁止复制）。

**决定**：**两个都不复制代码**，只借鉴设计。

**理由**：
- `douyin-robot` 法律上不能复制；
- `douyin-bot` 法律上可以，但它的实现带有已识别缺陷（昵称匹配、坐标点击、连接泄漏）；
- 统一为「都独立实现」比「一个复制一个不复制」更容易执行和检查。

**推翻条件**：确需复用 `douyin-bot` 某段代码时，单独记录决策并保留 MIT 声明。

## D-011 操作者接受风险，不做平台授权核查

**背景**：`Q-001` 要求核查平台条款。操作者明确表示：本项目为**个人学习用途**，不做授权核查。

**决定**：
- **不进行平台条款核查**——这是操作者的选择，不是遗漏；
- 操作者**已知情并接受后果**：账号可能被限流或封禁；
- 项目**按计划开发到 L1**，不做因条款未核查而降级；
- 平台条款与风险作为**事实记录**保留在 PRD §5.2，供将来回看。

**适用范围**：

| 项 | 内容 |
|---|---|
| 用途 | 个人学习、技术研究 |
| 账号归属 | **两个账号都属于操作者本人**（C-009） |
| 受影响第三方 | **无** |
| 商业化 / 对外服务 | 否 |
| 规避风控 | 不实现（不过验证码、不伪造指纹、不换 IP） |

**操作者已知情的内容**：

1. 抖音没有开放个人私信自动回复的官方接口；
2. 本项目通过浏览器自动化驱动网页版，可能不符合平台条款；
3. 平台可能在任何时候判定违规，导致账号被限流或封禁；
4. 后果由操作者承担，与参考项目的作者无关。

**理由**：
- 两个号都是操作者自己的，不存在误导他人或第三方知情权问题；
- 个人学习场景，账号风险是操作者自己资产的风险；
- 用「条款未核查」卡住开发，等于用操作者不认可的框架替操作者做决定。

**推翻条件**：
- 对话对象变为操作者之外的第三方 → 必须重新评估；
- 用途变为对外服务或批量使用 → 本决策不适用。

## D-013 不把平台合规判断塞进工程文档

**背景**：审查过程中曾出现一种倾向——把「平台是否授权」当成运行模式的开关，
推导出「项目终局是模拟系统」。这个结论越界了。

**决定**：
- 工程文档记录**事实**（平台条款现状、风险）与**决定**（操作者接受风险）；
- 但**不用合规判断去否决工程目标**；
- 真正该把关的是**工程安全**：不发错人、不重复发、能停下来、能恢复。

**理由**：
- 操作者已明确使用场景与风险承担；
- 继续用合规框架设卡，会让文档变成「劝退书」而不是「设计文档」；
- 工程文档的价值在于让实现正确，不在于替操作者做人生选择。

**边界**（这条决策不放开什么）：
- 不放开「对第三方账号自动操作」；
- 不放开「规避风控」（过验证码、伪造指纹、换 IP）；
- 不放开「批量/营销/对外服务」。

这些仍由 PRD §2.1 的硬性边界约束。

## D-012 AI 身份披露策略：不主动披露，被问时承认

**背景**：产品以「AI 小号」身份对话，需要明确是否披露 AI 身份。
对话对象为操作者自己的另一个账号（C-009），不涉及第三方知情权。

**决定**：
- **不主动披露**「我是 AI」；
- **被直接追问时如实承认**，不否认、不转移话题；
- 不编造超出人格设定的现实经历；
- 不声称执行了现实行动（「我已经到楼下了」这类）。

**理由**：
- 对话对象是操作者自己，不存在欺骗第三方的问题；
- 但「不主动披露」不等于「可以说任何话」——
  编造现实承诺（转账、到场）会产生真实的误导后果，即使对象是自己；
- 被问时承认，保留了人格设定的趣味性，同时避免了「死撑到底」的荒谬场景。

**与人格设定的关系**：

「人格稳定」不等于「必须让对方误以为是真人」。
人格设定负责**说话风格、背景事实、关系设定**，不负责**否认自身性质**。

**推翻条件**：对话对象变为操作者之外的第三方 → 需重新评估披露策略。
