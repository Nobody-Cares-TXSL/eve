## R-002 授权状态的处置决定（2026-10-23）

**触发**：操作者明确「本项目为个人学习用途，不需要做平台授权核查」。

**处置**：

| 维度 | 决定 | 依据 |
|---|---|---|
| 平台授权状态 | **保持 `unknown`** | 未核查，不能记为 `go` |
| 操作者风险接受 | **`accepted`** | D-011 |
| 运行模式 | **L1**（人工确认后发送） | 由上面两项推导 |
| L0 | **不允许** | 授权非 `go` 时始终禁止 |

**为什么不能直接把授权改成 `go`**：

「个人学习」是**使用目的**，不是平台的授权结论。把它写成 `go` 会：
1. 让文档声称一个没有证据的事实；
2. 使后续的「授权核查」失去意义——反正已经写成通过了；
3. 掩盖真实风险，让将来回顾时误判。

**为什么也不该强制停在 L3**：

L1 有**人工确认**环节，每条发送都有人看过，风险性质与 L0 完全不同。
在知情、低频、单账号、不对外的前提下，让操作者自主承担风险是合理的。

**受影响文档**：`PRD.md` §5/§9/§10、`DECISIONS.md` D-002/D-011、`AC.md` AC-0.4/AC-0.4b、
`CLI_SPEC.md` D10-D12。均已同步。

## R-003 CLAUDE.md 审查与授权边界修正（2026-10-23）

**触发**：对 `CLAUDE.md` 做只读审查，发现 R-002 的放行规则存在逻辑漏洞。

### P0：风险接受被当成了授权（已修正）

| 项 | 内容 |
|---|---|
| 问题 | R-002 允许 `unknown` + `accepted` 运行 L1/L2，理由是「L1 有人工确认」 |
| 漏洞 | **人工确认只覆盖发送，L1/L2 的读取都是自动的**。确认发送不能解决自动读取的授权问题 |
| 结论 | 风险接受回答「后果谁承担」，授权回答「动作是否被允许」，二者不可互换 |

**修正后的放行矩阵**：

```
授权 unknown + 任意  → L3              （当前）
授权 go      + 任意  → L0 / L1 / L2 / L3
授权 no-go   + 任意  → L3
```

**新增三层判断**（PRD §5.3.1）：

| 层 | 问题 | 当前 |
|---|---|---|
| 1 策略允许 | 授权放行了吗？ | `unknown` → 仅 L3 |
| 2 工程具备 | 代码实现了吗？ | 阶段 1 未开始 |
| 3 实际启用 | 完成启用检查？ | 未启用 |

三层为「与」关系。**层 1 未通过时，层 2/3 无论如何都不能让真实平台功能跑起来。**

**影响**：阶段 3 及之后的真实平台适配器在授权为 `unknown` 时**不得启用**。
项目最终交付物是「验证过架构的模拟系统」，这是明确接受的结局（D-011）。

## R-004 撤销「平台条款作为运行模式开关」（2026-10-23）

**触发**：操作者指出 R-003 的结论「项目终局是验证过架构的模拟系统」是错误的越界判断。

### 问题性质

R-003 修正了「风险接受 = 授权」的错误（这部分是对的），但**引入了新的越界**：

| 越界点 | 说明 |
|---|---|
| 把合规判断塞进工程文档 | 工程文档的职责是让实现正确，不是替操作者裁决项目是否成立 |
| 推导出项目终局 | 「只能 L3」→「最终是模拟系统」，这是用操作者不认可的框架给项目判死刑 |
| 忽略已确认的事实 | 两个账号都属于操作者本人，无第三方受影响；用途为个人学习 |

### 修正

**运行模式的上限改由「工程进度」决定，不由平台条款决定**：

| 模式 | 需要 | 何时具备 |
|---|---|---|
| L3 | CLI 骨架 + 状态机 | 阶段 1 |
| L2 | SQLite + 身份核验 + 读取 | 阶段 3 |
| **L1（产品形态）** | L2 + AI + 发送状态机 | 阶段 4 |
| L0 | L1 + 主动聊天 + 频率限制 | 阶段 6 之后 |

**保留的部分**：

- 平台条款与风险作为**事实记录**保留（PRD §5.2）；
- 操作者风险接受保留（D-011）；
- PRD §2.1 的硬性边界不变：单账号、只私信、只发文字、**不规避风控**；
- AC-0.4b 改为检查「不实现规避风控手段」——这是唯一保留的平台硬约束，
  因为它防的是「和平台对抗」，不是「使用自动化」。

**新增 D-013**：明确工程文档不承担合规裁决职责。

### 反思

这个问题反复了四次版本（初版 L1 → 强制 L3 → unknown+accepted→L1 → 只能 L3），
根因是**每次都在回答一个不该由文档回答的问题**。

正确的边界是：

| 谁来决定 | 什么 |
|---|---|
| 操作者 | 使用场景、是否接受账号风险 |
| 工程文档 | 怎么实现得正确、安全、可恢复 |
| 平台条款 | 操作者自己的知情事项，不是文档的否决开关 |

**受影响文档**：`PRD.md` §5/§9/§10、`DECISIONS.md` D-002/D-011/D-013、
`AC.md` AC-0.4/AC-0.4b、`CLI_SPEC.md` D10-D11、`CLAUDE.md`。均已同步。
