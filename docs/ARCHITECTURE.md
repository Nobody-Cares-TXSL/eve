# 架构设计 — ARCHITECTURE

> 版本：v1.2
> 状态：阶段 0 交付物（待确认）
> 覆盖范围：阶段 0～2 的系统地图；阶段 3～7 只给出边界，不提前设计接口

---

## 1. 设计原则

1. **CLI 优先**：所有能力通过命令暴露，不做常驻 Web 服务。
2. **纯逻辑与 I/O 分离**：判断「要不要回」这类逻辑必须不依赖浏览器，可单测。
3. **单一 Agent**：一个进程、一个会话、一个目标账号。不做编排。
4. **显式状态**：任何不确定的状态都必须能表示（`unknown` 是一等公民，不是异常分支）。
5. **失败即停**：无法确认安全时，暂停而不是重试。
6. **凭证零外泄**：登录态、聊天内容不进 git，不进日志明文。

## 3. 模块职责

> 命名遵循「不与标准库同名」规则（见 SOURCE_AUDIT §2.1）。
> 本表是**职责边界**，不是最终文件名。

| 模块 | 职责 | 不负责 | 可测性 |
|---|---|---|---|
| `cli` | 参数解析、子命令分发、退出码 | 业务逻辑 | 集成测试 |
| `config` | 加载、强类型校验、默认值 | 运行时热更新 | 单测 |
| `page` | 浏览器生命周期、登录态、页面操作 | 业务判断 | 需浏览器（mock） |

| `send` | 发送状态机、结果确认 | 生成内容 | **单测**（状态转换） |
| `db` | SQLite schema、事务、迁移 | 业务规则 | **单测**（内存库） |
| `log` | 运行日志、审计日志 | 业务逻辑 | — |

## 4. 完整消息链（阶段 2 完成后）

这是本项目的**主链路**，每个阶段都在补强其中的一段。

```
[1] 轮询触发
     │  CLI run 启动单轮循环（间隔由配置驱动，且有测试保证）
     ▼
[2] 会话定位
     │  按抖音号找到目标会话（昵称仅作提示）
     ▼
[3] 身份核验  ◄── 身份不确定 → 停止，不读取
     │  抖音号 == 白名单唯一项？
     ▼
[4] 读取消息
     │  取页面当前可见气泡，转成消息事件列表
     ▼
[5] 归档（阶段 2 核心）
     │  与 SQLite 已有记录做增量对齐
     │  ├─ 能匹配 → 只写入新增尾部
     │  └─ 无法匹配 → 按规则处理（见 §6）
     ▼
[6] 决策（阶段 4）
     │  最新一条是否为「对方发来的、未处理过的」事件？
     ▼
[7] 生成（阶段 4）
     │  AI 调用，超时/失败 → 本轮放弃，不发送
     ▼
[8] 发送前检查（阶段 4）
     │  长度 / 内容过滤 / 频率上限 / 目标仍为同一人
     ▼
[9] 发送（阶段 4）
     │  sent / failed / unknown
     ▼
[10] 记录
       审计日志 + 事件状态 + 计数
```

**阶段 2 的退出条件就是让 [5] 可靠；阶段 3 是让 [3][4] 可靠。**

## 5. 数据职责划分

> 具体表结构在阶段 2 的 Contract 中定义。这里只定**职责边界**，避免提前锁死。

| 概念 | 职责 | 关键约束 |
|---|---|---|
| **目标账号** | 唯一白名单项 | 只能有 1 条；抖音号必填 |
| **消息事件** | 一条实际发生的消息 | 需要「事件身份」，不能只用文本 |
| **归档游标** | 已确认归档到的位置 | 崩溃后可恢复 |
| **回复记录** | 我方发出的一条消息 | 带发送三态 |
| **频率计数** | 小时/日维度的已发送数 | 独立于事件表 |

### 5.1 「消息内容相同」≠「消息事件相同」

这是阶段 2 最容易做错的地方。必须区分：

- **内容相同**：两条消息文本一模一样；
- **事件相同**：同一条消息被读了两次。

判据优先级：

1. 若输入提供了稳定消息 ID → **以 ID 为准**（唯一可靠判据）；
2. 否则用「发送方 + 内容 + 相对位置 + 邻居」的组合指纹；
3. 滑动窗口对齐只作为**找不到 ID 时的兜底**。

> **稳定 ID 是可选输入，不是阶段 2 的前提条件。**
>
> 阶段 2 的 Contract **从一开始就支持两种模式**：
> - `id_mode`：输入含稳定 ID，归档结果完全确定；
> - `no_id_mode`：输入无 ID，使用组合指纹 + 滑动窗口，**允许产生 `ambiguous` 结果**。
>
> 阶段 3 负责验证真实平台能否提供 ID，**不决定阶段 2 能否开始**。
> 若阶段 3 发现需要改变 Contract，走正式的设计变更记录（DECISIONS.md），
> 不在实现中悄悄改。

### 5.2 归档结果的三态

> 初版承诺「不重复、不丢失」，这个保证在**没有稳定 ID** 时不可能普遍成立。
> 必须把不确定性显式表达出来，而不是假装它不存在。

| 结果 | 含义 | 条件 |
|---|---|---|
| `matched` | 能可靠识别为已有消息 | 有 ID，或组合指纹唯一匹配 |
| `new` | 能可靠判定为新增 | 有 ID 且未见过，或对齐后有明确增量 |
| `ambiguous` | **现有信息不足以判断** | 无 ID 且对齐失败/多解 |

**`ambiguous` 的处理规则**：

1. **不静默丢弃**：写入待确认表，保留原始输入；
2. **不自动处理**：该条消息不参与去重判定，不触发 AI 回复；
3. **记录并告警**：写 `WARN` 日志，`status` 中可见计数；
4. **等人工或阶段 3 的能力补齐**后再处理。

> **可验证的承诺**（替代「不重复不丢失」）：
> - 对**相同输入**，归档结果**确定且可重复**（AC-2.2）；
> - 遇到无法确认的情况，**不静默丢弃**（AC-2.8）；
> - 在 `id_mode` 下，保证不重复、不丢失；
> - 在 `no_id_mode` 下，保证「不丢数据」和「结果确定」，**不保证**「无歧义」。

### 5.3 归档层与身份核验层的边界

> 归档层**不判断对方是谁**。身份由调用方核验后传入。

**归档接口的输入契约**：

| 字段 | 要求 |
|---|---|
| `conversation_ref` | **必须**是调用方已核验的会话标识（如抖音号） |
| 消息列表 | 只包含该会话的消息 |

**归档层禁止做的事**：

1. ❌ 从昵称推断对方身份；
2. ❌ 接受未核验的 `conversation_ref`（空值、`None`、占位符一律拒绝）；
3. ❌ 自行决定「这条消息属于谁」；
4. ❌ 跨 `conversation_ref` 合并数据。

**调用方的责任**：

- 身份不确定时，**不得调用归档**；
- 身份核验失败时，整轮跳过，不读不写。

> 阶段 2 的测试用**模拟的已核验会话标识**，因此可以独立于阶段 3 开发和验收。
> 阶段 3 接入真实身份核验后，归档层代码不需要改动。

## 6. 归档的关键场景（阶段 2 必须覆盖）

| 场景 | 期望行为 |
|---|---|
| 连续两条内容完全一样 | 记为两个事件，不是一条（`id_mode` 确定；`no_id_mode` 可能 `ambiguous`） |
| 双方都发送「好」 | 按发送方区分，互不干扰 |
| 页面刷新后重现已存消息 | 不重复入库 |
| 聊天窗口只显示最近一段 | 只补增量，不删除旧记录 |
| 归档中途进程退出 | 重启后从游标恢复，无半写状态 |
| 首次归档（库为空） | 全量写入，建立游标 |
| **本次读取与已有归档完全无重叠** | 按 Contract 规定处理（追加并标记 `gap`），**不静默丢弃** |

> **消息删除/撤回检测不在阶段 2 范围**。`PRD.md` §4 已将其列为非目标，
> 初版此处与之冲突，已删除该项。若未来需要，先改 PRD 与 AC。

## 7. 发送状态机（阶段 4 边界）

```
         ┌──────────┐
         │ pending  │  已决定发送，尚未执行
         └────┬─────┘
              │ 执行点击
       ┌──────┼──────┐
       ▼      ▼      ▼
   ┌──────┐┌──────┐┌─────────┐
   │ sent ││failed││ unknown │
   └──────┘└──┬───┘└────┬────┘
              │         │
       可安全重试    不重试
              │         │
              ▼         ▼
         退避重试    暂停 + 人工核对
```

**`unknown` 绝不能自动重试。** 原因：无法区分「消息没发出去」和「发出去了但没确认到」，重试会导致对方收到两条。

## 8. 运行状态（阶段 1 定义，阶段 7 扩展）

CLI `status` 必须能明确回答「现在是什么状态」。**状态必须互斥且可区分**：

| 状态 | 含义 | 进程是否存活 | 恢复方式 |
|---|---|---|---|
| `stopped` | 未运行 / 已正常退出 | ❌ 否 | `run` |
| `running` | 正常轮询 | ✅ 是 | — |
| `pause_requested` | 已请求暂停，等待当前轮结束 | ✅ 是 | 等待（自动转 `paused_manual`） |
| `paused_manual` | 人工暂停，**进程仍存活** | ✅ 是 | `resume` |
| `paused_auth` | 登录失效，**进程已退出** | ❌ 否 | 重新登录后 `run` |
| `paused_risk` | 遇到验证码/风控，**进程已退出** | ❌ 否 | 人工处理后 `run` |
| `paused_env` | 网络/页面持续失败，重试耗尽，**进程已退出** | ❌ 否 | 修复环境后 `run` |
| `paused_unknown` | 发送结果未知，**进程已退出** | ❌ 否 | 人工核对后 `run` |
| `error` | 不可恢复错误，进程已退出 | ❌ 否 | 看日志 |

**四条关键区分**：

1. **`paused_manual` ≠ `stopped`**。前者进程还在、可 `resume`；后者进程已退出，只能 `run`。
   若混淆，CLI 无法判断「该 resume 还是该重新 run」。
2. **`pause_requested` 是过渡态**。它不是最终状态，最长存在一个轮询周期。
3. **`paused_manual` 进程存活，其余 `paused_*` 进程退出**。
   区别在于：人工暂停可以就地恢复；而登录失效、风控、结果未知都需要**人工完成外部动作**
   （扫码、过验证、核对消息），进程留着没有意义，退出反而让 systemd 能通过退出码判断「不要重启」。
4. **所有 `paused_*` 都不是 `error`**。它们是**预期内**的暂停，退出码统一为 `3`（需要人工介入），
   只有 `error` 才对应非预期失败。

> 阶段 1 只需实现 `stopped` / `running` / `pause_requested` / `paused_manual` / `paused_auth`。
> `paused_risk` / `paused_env` 由阶段 3 引入，`paused_unknown` 由阶段 4 引入，
> 但状态位在阶段 1 就预留。

## 9. 与 systemd 的关系（阶段 7）

- 进程退出码区分「正常退出」「需要人工介入」「可重试错误」；
- `Restart=on-failure` 只对可重试错误生效；
- 需要人工介入时**退出码让 systemd 不重启**，避免刷屏与反复撞风控。

具体映射在阶段 7 定义，但阶段 1 就要预留退出码语义。

## 10. 明确不做的事

- 不做配置热更新（改配置 → 重启）
- 不做数据库在线迁移（阶段 2 用版本号 + 启动时检查）
- 不做多进程/多实例（单实例，用锁文件防重复启动）
- 不做 Web 界面
- 不做插件系统
