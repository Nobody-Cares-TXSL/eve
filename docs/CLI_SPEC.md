## 0. 阶段 1 的边界

**本阶段不做的事**（写在这里是为了防止实现时顺手加进去）：

- ❌ 不连接真实抖音
- ❌ 不实现 `login`（命令名预留，执行时明确告知「阶段 3 提供」）
- ❌ 不读写真实消息
- ❌ 不调用 AI
- ❌ 不建 SQLite 库（阶段 2）

**本阶段要做的事**：

- ✅ 可诊断：`doctor` 逐项报告环境与配置
- ✅ 可观察：`status` 区分所有运行状态
- ✅ 可控制：`pause` / `resume` 可靠切换状态
- ✅ 可安全运行：`run` 跑一个**不碰抖音**的空转循环，用于验证控制逻辑
- ✅ 单实例保护
- ✅ 严格退出码

> `run` 在阶段 1 是**测试手段**，不是产品形态。它验证「状态机 + 循环 + 信号处理」，
> 后续阶段把真实的「读→归档→决策→生成→发送」插进这个循环骨架。

## 2. `doctor`

### 2.1 作用

回答一个问题：**「这台机器现在能不能跑这个程序？」**
逐项检查，每项独立报告，不因为一项失败就中断。

### 2.2 检查项

| 编号 | 检查 | 通过条件 | 失败级别 |
|---|---|---|---|
| D1 | Python 版本 | ≥ 3.11 | `FAIL` |
| D2 | 依赖可用 | `playwright`、`httpx` 可导入 | `WARN`（阶段 1）→ `FAIL`（阶段 3 起） |
| D3 | 模块命名 | 无 `.py` 文件名与 `sys.stdlib_module_names` 冲突 | `FAIL` |
| D4 | 配置结构 | 配置文件存在且字段合法 | `FAIL` |
| D5 | 数据目录 | 可创建、可写 | `FAIL` |
| D6 | 日志目录 | 可创建、可写 | `FAIL` |
| D7 | 单实例锁 | 无其他实例占用 | `WARN` |
| D8 | 目标账号 | `target.douyin_id` 已填写 | `WARN` |
| D9 | 登录凭证 | 凭证文件存在 | `WARN` |

**级别语义**：

- `FAIL`：阻塞 `run`，`doctor` 退出码 `2`
- `WARN`：不阻塞 `doctor`，但可能阻塞 `run`（属于「运行条件缺失」或「阶段未到」）
- `OK`：通过

> **D2 在阶段 1 为 `WARN`**：`playwright` / `httpx` 阶段 3 才真正需要，
> 阶段 1 检测它们只是「提前告知」，不应阻塞骨架开发。阶段 3 起升为 `FAIL`。
>
> **D8/D9 为 `WARN`**，依据 D-007：**配置校验与运行条件分离**。
> 阶段 1 尚未填写目标账号时，`doctor` 仍应能完整跑完。

### 2.3 输出格式

人类可读的表格，每行一项：

```
[OK]   D1 Python 版本         3.12.3 (>= 3.11)
[OK]   D2 依赖可用            playwright, httpx
[OK]   D3 模块命名            无冲突
[FAIL] D4 配置结构            config/config.json 不存在
                              → 修复：cp config/config.example.json config/config.json
[OK]   D5 数据目录            /home/user/.local/share/dac
[OK]   D6 日志目录            /home/user/.local/share/dac/logs
[WARN] D8 目标账号            未配置 target.douyin_id
                              → 说明：阶段 3 前无需填写，不影响只读命令

结论：存在 1 项 FAIL，无法运行。
```

### 2.4 退出码

| 情况 | 退出码 |
|---|---|
| 全部 `OK` 或仅 `WARN` | `0` |
| 存在 `FAIL` | `2` |

### 2.5 `--json`

输出机器可读 JSON，供测试断言使用：

```json
{
  "checks": [
    {"id": "D1", "level": "ok", "detail": "3.12.3"},
    {"id": "D4", "level": "fail", "detail": "config/config.json 不存在", "fix": "cp ..."}
  ],
  "summary": {"fail": 1, "warn": 0, "ok": 8}
}
```

> AC-1.1、AC-1.2、AC-1.3 的自动化测试**只依赖 `--json`**，不解析人类可读输出。

## 3. `status`

### 3.1 作用

回答一个问题：**「现在程序处于什么状态，我下一步该做什么？」**

### 3.2 输出

```
状态：paused_manual
说明：已人工暂停，进程仍在运行（PID 12345，已校验存活）
自：2026-10-23 14:03:11（已暂停 8 分钟）
建议：执行 `dac resume` 恢复，或 `dac stop` 退出

最近事件：
  14:03:11  收到暂停请求
  14:03:14  当前轮结束，进入 paused_manual
```

**进程已死时的输出**（状态被降级）：

```
状态：stopped
说明：上次进程已退出（PID 12345 不存在），可能是异常终止
      记录的原状态为 paused_manual
自：2026-10-23 14:03:11
建议：执行 `dac run` 重新启动

最近事件：
  14:03:11  收到暂停请求
  14:03:14  当前轮结束，进入 paused_manual
  15:20:02  [status] 检测到 PID 12345 已不存在，降级为 stopped
```

### 3.3 状态与建议的映射

| 状态 | 建议动作 |
|---|---|
| `stopped` | `dac run` |
| `running` | `dac pause` 或 `dac status --watch` |
| `pause_requested` | 等待，通常数秒内转为 `paused_manual` |
| `paused_manual` | `dac resume` 或 `dac stop` |
| `paused_auth` | 重新登录（阶段 3）后 `dac run` |
| `paused_risk` | 人工处理验证后 `dac run` |
| `paused_unknown` | 人工核对消息后 `dac run` |
| `error` | `dac logs --tail 50` |
| **PID 已死（降级）** | `dac run`（并检查 `dac logs` 确认退出原因） |

> `status` 显示的每个状态都必须经过 PID 存活校验（§5.4）。
> 状态文件里的 `pid` 字段**不可信**，必须实际检查。

### 3.4 退出码

| 情况 | 退出码 |
|---|---|
| 成功读取状态 | `0` |
| 状态文件不存在或损坏 | `2` |

> `status` 对任何**已识别**的运行状态都返回 `0`——状态本身不是错误。
> 只有「读不到状态」才是错误。

## 4. `run`

### 4.1 作用

启动前台运行循环。

### 4.2 阶段 1 的行为

```
1. 获取单实例锁（失败 → 退出码 4）
2. 加载配置（结构错误 → 退出码 2）
3. 检查运行条件（目标账号/凭证缺失 → 退出码 3）
4. 写状态文件：running
5. 循环：
     a. 检查控制文件（pause/stop 请求）
     b. 执行一轮「空转」（阶段 1 只记录心跳，不碰抖音）
     c. 按配置间隔休眠（可被信号打断）
6. 退出时写状态文件
```

### 4.3 暂停的精确语义

`pause` 不是立即停止，而是**让当前轮自然结束**：

```
收到 pause 请求
  → 状态写为 pause_requested
  → 当前轮继续执行完
  → 状态写为 paused_manual
  → 循环挂起，等待控制文件变化
```

**为什么不在轮次中间中断**：后续阶段一轮里包含「读消息 → 归档 → 发送」，
中途打断会留下半完成状态。**只在轮次边界检查控制信号**，是保证状态一致的前提。

### 4.4 挂起与恢复的机制

> 这一节定义 `resume` **如何真正唤醒进程**，而不只是改状态字段。

#### 挂起期间的行为

进程进入 `paused_manual` 后，**不退出、不做业务**，只做一件事：**轮询控制文件**。

| 参数 | 值 | 说明 |
|---|---|---|
| 轮询方式 | 轮询 `control.json` 的 mtime | 不依赖 inotify，避免跨文件系统兼容问题 |
| 轮询间隔 | `pause_poll_seconds`，默认 **2 秒** | 独立于 `cycle_seconds`，可配置 |
| 每次轮询动作 | 读 `control.json` → 判断意图 | 不做任何消息/页面操作 |
| 资源占用 | 每 2 秒一次文件 stat，可忽略 | — |

**为什么不用信号**：`CLI_SPEC` §5.1 已规定控制命令只写文件、不操作进程。
挂起进程因此必须主动轮询，这是该设计的必然结果。

#### `resume` 的完整语义

`resume` 不是「把状态改回 running」，而是**一个跨进程握手**：

```
[resume 进程]
  1. 读 state.json，确认状态为 paused_manual
  2. 确认 PID 存活（否则报错，见 §5.4）
  3. 写 control.json: {"intent": "resume", "requested_at": <ts>, "request_id": <uuid>}
  4. 等待 state.json 变为 running（最多等 3 × pause_poll_seconds）
     ├─ 成功 → 输出「已恢复运行」，退出码 0
     └─ 超时 → 输出「恢复请求已写入，但进程未响应」
                + 提示「执行 dac status 查看，或 dac stop 后重新 dac run」
                + 退出码 4（可重试）
```

```
[挂起中的 run 进程]
  1. 每 pause_poll_seconds 读 control.json
  2. 发现 intent=resume 且 request_id 未被消费
  3. 标记 request_id 已消费（写回 control.json）
  4. 状态 paused_manual → running
  5. 回到正常轮次循环，从下一轮开始
```

**关键约束**：

1. `resume` 必须**等待确认**，不能写完文件就报成功——否则用户会以为已恢复。
2. `request_id` 防止重复消费：同一意图只生效一次。
3. 若进程无响应，`resume` 返回退出码 `4`，**不自行 kill 进程**。

#### 不补跑

恢复后从**下一轮**开始，不补跑暂停期间错过的轮次。错过就是错过，不累积。

> 理由：补跑会在短时间内集中发出多条消息，是风控高危行为，也违背「像真人」的产品目标。

### 4.5 暂停期间的资源

| 资源 | 挂起时状态 |
|---|---|
| CPU | 每 2 秒一次 stat，可忽略 |
| 浏览器（阶段 3 起） | **保持打开**（重新打开成本高且可能触发风控） |
| 数据库连接 | 保持 |
| 单实例锁 | **保持持有**（防止暂停时被第二个实例抢占） |

### 4.6 信号处理

| 信号 | 行为 |
|---|---|
| `SIGINT` / `SIGTERM` | 等同 `stop`：当前轮结束后退出，状态 `stopped`，退出码 `0` |
| 第二次 `SIGINT` | 立即退出，状态 `stopped`，退出码 `0`（用户明确要求强退） |
| `SIGHUP` | 忽略（防止终端断开误杀） |

### 4.7 退出码（`run`）

| 情况 | 退出码 | 状态 |
|---|---|---|
| 正常停止（`stop` / 信号） | `0` | `stopped` |
| 配置结构错误 | `2` | — |
| 运行条件缺失（无账号/无凭证） | `3` | — |
| 登录失效（阶段 3 起） | `3` | `paused_auth` |
| 单实例锁被占用 | `4` | — |
| 可重试的运行时错误 | `4` | — |
| 不可恢复错误 | `1` | `error` |

## 5. `pause` / `resume` / `stop`

### 5.1 实现方式

三个命令都**不直接操作进程**，只写控制文件；由 `run` 循环读取。

**但 `resume` 额外要求等待确认**（§4.4），因为「写文件」不等于「进程已恢复」。

| 命令 | 写什么 | 前置状态 | 是否等待确认 | 成功退出码 |
|---|---|---|---|---|
| `pause` | `{"intent":"pause", ...}` | 必须是 `running` | 否（异步生效） | `0` |
| `resume` | `{"intent":"resume", "request_id":...}` | 必须是 `paused_manual` | **是**（最多 3 × `pause_poll_seconds`） | `0`（确认）/ `4`（超时） |
| `stop` | `{"intent":"stop", ...}` | `running` / `paused_manual` / `pause_requested` | 否 | `0` |

**为什么 `pause` 不等待、`resume` 要等待**：

- `pause` 需要等当前轮跑完，轮次长度不定，同步等待会让命令卡住；
- `resume` 只是唤醒挂起进程，最多等一个轮询间隔，等待代价小，而**不等待会让用户误判**。

**状态不匹配时**（如对 `stopped` 执行 `pause`）：

```
错误：当前状态为 stopped，无法 pause。
建议：执行 `dac run` 启动。
```

退出码 `2`。

### 5.2 控制文件格式

```json
{
  "intent": "resume",
  "request_id": "7c3e9a21",
  "requested_at": "2026-10-23T14:03:11+08:00",
  "consumed_by": null
}
```

| 字段 | 作用 |
|---|---|
| `intent` | `pause` / `resume` / `stop` |
| `request_id` | 幂等键，防止同一意图被重复消费 |
| `requested_at` | 用于 `status` 展示「请求于何时」 |
| `consumed_by` | 被 `run` 消费后写入消费方标识与时间 |

**写入必须原子**：写临时文件 → `os.replace()`。禁止直接覆盖，避免读到半个 JSON。

### 5.3 为什么用文件而不是信号

- 信号无法携带语义（`SIGUSR1` 容易被误解释）；
- 文件可被 `status` 读取，形成「状态可观察」的闭环；
- 跨进程重启后控制意图仍在，不会丢失；
- `request_id` 提供幂等性，信号做不到。

> 控制文件放在数据目录下，与状态文件同一处，生命周期一致。

### 5.4 PID 存活校验

状态文件记录 `pid` 与 `started_at`。**任何命令读取状态时都必须校验 PID**：

```
读取 state.json
  → 状态为 stopped / error          → 直接使用
  → 状态为 running / pause_requested / paused_manual
      → 检查 pid 是否存在且可 signal(0)
          ├─ 存活 → 使用记录的状态
          └─ 已死 → 降级为 stopped
                    + 标注「上次进程已退出（PID 12345 不存在），可能是异常终止」
                    + 记录 WARN 日志
  → 状态为 paused_auth / paused_risk / paused_unknown
      → 这些状态本应无进程，若 pid 仍存活 → 标注「状态与进程不一致，请检查」
```

**为什么必须校验**：PID 会被系统复用。若只信状态文件，可能对**别人的进程**发信号或报告假状态。

> 校验函数放在 `infra/state_file.py`，`status` / `run` / `control` 共用，不得各自实现。

## 6. `logs`

### 6.1 用法

```
dac logs                 # 最近 50 行
dac logs --tail 200      # 最近 200 行
dac logs --follow        # 持续跟随
dac logs --level WARN    # 只看 WARN 及以上
```

### 6.2 日志不得包含的内容（硬性）

| 禁止 | 原因 |
|---|---|
| Cookie 值、`sessionid`、`passport_auth_status` | 凭证泄露即账号失守 |
| API Key | 同上 |
| 完整聊天消息正文 | 隐私；日志可能被分享用于排障 |
| 对方昵称全称 | 可关联到真实身份 |

**允许的替代写法**：

```
# ❌
消息内容: 我明天去医院复查，你陪我去吗
# ✅
消息已归档: friend=7f3a2c, len=18, fp=9b1e
```

> 正文只存在于数据库；日志只记**事件与标识**。

### 6.3 日志格式

单行、结构化、可 grep：

```
2026-10-22T14:03:11+0800 INFO  run.cycle       cycle=12 state=running
2026-10-22T14:03:12+0800 INFO  run.pause       pause requested, waiting for cycle boundary
2026-10-22T14:03:14+0800 INFO  run.state       running -> paused_manual
```

## 7. 路径约定

| 项 | 默认值 | 覆盖方式 |
|---|---|---|
| 配置文件 | `./config/config.json` | `--config` |
| 数据目录 | `$XDG_DATA_HOME/dac` 或 `~/.local/share/dac` | `--data-dir` |
| 状态文件 | `<data-dir>/state.json` | — |
| 控制文件 | `<data-dir>/control.json` | — |
| 锁文件 | `<data-dir>/run.lock` | — |
| 日志目录 | `<data-dir>/logs/` | — |

**所有路径必须是绝对路径**，避免工作目录变化导致状态文件「丢失」。

## 8. 退出码总表（AC-1.7）

| 码 | 含义 | systemd 应否重启 |
|---|---|---|
| `0` | 正常 | 否 |
| `1` | 不可恢复错误 | 否（需人工看日志） |
| `2` | 配置错误 / 命令用法错误 | 否（重启也会同样失败） |
| `3` | 需要人工介入（条件缺失、登录失效、风控、结果未知） | **否**（否则反复撞同一问题） |
| `4` | 可重试错误（锁冲突、临时网络故障） | 是 |

> 这个表是阶段 7 systemd 配置的唯一依据。阶段 1 必须严格实现，不能事后补。
