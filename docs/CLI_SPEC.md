## 0. 阶段 1 的边界

**本阶段不做的事**（写在这里是为了防止实现时顺手加进去）：

- ❌ 不连接真实抖音
- ❌ 不实现 `login`（命令名预留，执行时明确告知「阶段 3 提供」）
- ❌ 不读写真实消息
- ❌ 不调用 AI
- ❌ 不建 SQLite 库（阶段 2）

**本阶段要做的事**：

- ✅ 可诊断：`doctor` 逐项报告环境与配置
- ✅ 可观察：`status` 区分所有运行状态
- ✅ 可控制：`pause` / `resume` 可靠切换状态
- ✅ 可安全运行：`run` 跑一个**不碰抖音**的空转循环，用于验证控制逻辑
- ✅ 单实例保护
- ✅ 严格退出码

> `run` 在阶段 1 是**测试手段**，不是产品形态。它验证「状态机 + 循环 + 信号处理」，
> 后续阶段把真实的「读→归档→决策→生成→发送」插进这个循环骨架。

## 2. `doctor`

### 2.1 作用

回答一个问题：**「这台机器现在能不能跑这个程序？」**
逐项检查，每项独立报告，不因为一项失败就中断。

### 2.2 检查项

| 编号 | 检查 | 通过条件 | 失败级别 |
|---|---|---|---|
| D1 | Python 版本 | ≥ 3.11 | `FAIL` |
| D2 | 依赖可用 | `playwright`、`httpx` 可导入 | `WARN`（阶段 1）→ `FAIL`（阶段 3 起） |
| D3 | 模块命名 | **`src/` 下**无 `.py` 文件名与 `sys.stdlib_module_names` 冲突 | `FAIL` |
| D4 | 配置结构 | 配置文件存在且字段合法 | `FAIL`（存在未知字段时可 `WARN`） |
| D5 | 数据目录 | 目录**已存在且可写**，或可创建 | `FAIL` |
| D6 | 日志目录 | 目录**已存在且可写**，或可创建 | `FAIL` |
| D7 | 单实例锁 | 无其他实例占用；只读探测，不获取锁 | `WARN`（发现占用或残留锁文件时） |
| D8 | 目标账号 | `target.douyin_id` 已填写 | `WARN`（未配置） |
| D9 | 登录凭证 | `login.credentials_file` 指向存在的文件 | `WARN`（未配置或文件不存在） |
| D10 | 运行模式 | `runtime.mode` 是合法模式，且不超过当前工程阶段上限 | `FAIL`（非法或超过上限）；`WARN`（未声明） |
| D11 | 风险接受 | `risk.acceptance` 已声明为 `accepted` | `WARN`（未声明或为 `not-accepted`） |

**级别语义**：

- `FAIL`：阻塞 `run`，`doctor` 退出码 `2`
- `WARN`：不阻塞 `doctor`，但可能阻塞 `run`（属于「运行条件缺失」或「阶段未到」）
- `OK`：通过

> **D2 在阶段 1 为 `WARN`**：`playwright` / `httpx` 阶段 3 才真正需要，
> 阶段 1 检测它们只是「提前告知」，不应阻塞骨架开发。阶段 3 起升为 `FAIL`。
>
> **D8/D9 为 `WARN`**，依据 D-007：**配置校验与运行条件分离**。
> 阶段 1 尚未填写目标账号时，`doctor` 仍应能完整跑完。

#### D3 的扫描范围（防止误报）

```
扫描根：<repo>/src/
递归：是
包含：所有 *.py
排除：以 .gitignore 匹配的路径
排除：__pycache__、.venv、venv
判定：文件 stem（不含 .py）∈ sys.stdlib_module_names → FAIL
```

**为什么必须限定范围**：仓库根目录下有 `douyin-bot/`、`douyin-robot/` 两个参考项目，
其中 `douyin-robot/src/selectors.py` 与标准库同名。若全仓库扫描，`doctor` 会永远报 `FAIL`，
而那个文件**不属于本项目**，也不参与运行。

> 实现必须与 `.gitignore` 保持一致：被忽略的目录不扫描。
> 若 `.gitignore` 缺失，退化为只扫 `src/`。

#### D5 / D6 的判定顺序

```
1. 目录不存在 → 尝试创建
     ├─ 创建成功且可写 → OK
     └─ 创建失败 → FAIL（附具体 errno）
2. 目录已存在
     ├─ 可写 → OK
     └─ 不可写 → FAIL（附路径与权限说明）
```

**不能只测「能否创建」**：目录已存在但只读是最典型的权限故障，必须单独覆盖。

#### D7 的检测方式

`doctor` **只读探测，不获取锁**。

```
1. 锁文件不存在 → OK
2. 锁文件存在
     ├─ 尝试以「非阻塞」方式获取锁（flock LOCK_EX | LOCK_NB）
     │    ├─ 获取成功 → 立即释放 → WARN「锁文件存在但无人持有（上次未清理，run 会复用）」
     │    └─ 获取失败 → WARN「已有实例在运行」
```

**关键规则**：

1. **绝不删除锁文件。** 对 `flock` 而言，文件存在 ≠ 锁被持有。
   删除文件会让后续进程锁住**不同的 inode**，两个实例同时「持有锁」，单实例保证失效。
2. **「锁文件存在」与「锁被占用」是两个不同的事实**，必须分开报告。
3. `doctor` 获取锁后**立即释放**，不做任何业务。
4. 探测必须用非阻塞模式（`LOCK_NB`），否则会卡住。

> 这条规则同样适用于 `run`：`run` 启动时若锁文件存在但无人持有，
> **直接复用该文件**，不删除、不重建。

### 2.3 输出格式

人类可读的表格，每行一项：

**场景一：干净目录，配置缺失**（实际运行输出）

```
[OK]   D1  Python 版本      3.12.3 (要求 >= 3.11)
[WARN] D2  依赖可用         缺少 playwright、httpx（阶段 1 暂不阻塞）
[OK]   D3  模块命名         无标准库同名模块
[FAIL] D4  配置结构         配置文件不存在：/path/to/config.json
                            → 修复：按 docs/CLI_SPEC.md §7.1 创建配置，并填写必需字段 cycle_seconds
[OK]   D5  数据目录         /path/to/data
[OK]   D6  日志目录         /path/to/data/logs
[OK]   D7  单实例锁         未发现运行锁文件
[WARN] D8  目标账号         配置不可用，未检查目标账号（见 D4）
[WARN] D9  登录凭证         配置不可用，未检查登录凭证（见 D4）
[WARN] D10 运行模式         配置不可用，未检查 runtime.mode（见 D4）
[WARN] D11 风险接受         配置不可用，未检查 risk.acceptance（见 D4）

结论：1 项 FAIL、5 项 WARN、5 项 OK；doctor 退出码 2。
```

**场景二：配置合法但可选字段未填**

D4 为 `OK`；D8/D9 报「未配置…（阶段 3 前无需填写）」；D10/D11 报「未声明…」。
四项均为 `WARN`，退出码 `0`。

### 2.4 退出码

| 情况 | 退出码 |
|---|---|
| 全部 `OK` 或仅 `WARN` | `0` |
| 存在 `FAIL` | `2` |

### 2.5 `--json`

输出机器可读 JSON，供测试断言使用：

```json
{
  "checks": [
    {"id": "D1", "level": "ok", "detail": "3.12.3 (要求 >= 3.11)"},
    {"id": "D2", "level": "warn", "detail": "缺少 playwright、httpx（阶段 1 暂不阻塞）", "fix": "阶段 3 起安装 requirements.txt"},
    {"id": "D3", "level": "ok", "detail": "无标准库同名模块"},
    {"id": "D4", "level": "fail", "detail": "配置文件不存在：/path/to/config.json", "fix": "按 docs/CLI_SPEC.md §7.1 创建配置，并填写必需字段 cycle_seconds"},
    {"id": "D5", "level": "ok", "detail": "/path/to/data"},
    {"id": "D6", "level": "ok", "detail": "/path/to/data/logs"},
    {"id": "D7", "level": "ok", "detail": "未发现运行锁文件"},
    {"id": "D8", "level": "warn", "detail": "配置不可用，未检查目标账号（见 D4）"},
    {"id": "D9", "level": "warn", "detail": "配置不可用，未检查登录凭证（见 D4）"},
    {"id": "D10", "level": "warn", "detail": "配置不可用，未检查 runtime.mode（见 D4）"},
    {"id": "D11", "level": "warn", "detail": "配置不可用，未检查 risk.acceptance（见 D4）"}
  ],
  "summary": {"fail": 1, "warn": 5, "ok": 5}
}
```

**JSON 契约（测试依赖）**：

| 项 | 保证 |
|---|---|
| `checks` 顺序 | 严格 `D1` → `D11`，共 11 项，不增不减 |
| `checks[].id` | `D1`…`D11` |
| `checks[].level` | `ok` / `warn` / `fail` |
| `checks[].detail` | 非空字符串 |
| `checks[].fix` | 仅在有修复建议时出现，可为空 |
| `summary` | 三个键 `fail` / `warn` / `ok`，各自计数**必须**与 `checks` 逐条统计一致 |

> 配置缺失或损坏时，D8～D11 **仍然输出**，内容为「配置不可用，未检查…（见 D4）」，
> 级别为 `warn`——不得因 D4 失败而让这四项消失或抛异常。

> AC-1.1、AC-1.2、AC-1.3 的自动化测试**只依赖 `--json`**，不解析人类可读输出。

### 2.6 `doctor` 的副作用边界

> 初版称 `doctor` 为「只读」，但 D5/D6 又要尝试创建目录——自相矛盾。
> 这里明确允许的副作用范围。

**`doctor` 允许的副作用（仅此一项）**：

| 允许 | 说明 |
|---|---|
| 创建数据目录、日志目录 | 为了验证「能否创建」，必须真的尝试 |

**`doctor` 禁止的副作用**：

| 禁止 | 原因 |
|---|---|
| 写状态文件、控制文件 | 会干扰正在运行的实例 |
| 获取单实例锁 | 会阻塞 `run` |
| 写日志文件 | `doctor` 的输出直接打到 stdout；只有 `FAIL`/`WARN` 才写一行到日志 |
| 创建配置文件 | 只报告缺失，不代替用户做决定 |
| 删除任何文件（含残留锁） | 见 §2.2 D7 与 §5.5 |

**为什么不干脆禁止创建目录**：

D5/D6 的检查目的是「`run` 时能不能用」。若只检查父目录权限而不实际创建，
会漏掉「父目录可写但同名文件已存在」「磁盘满」等情况。

> **权衡**：允许创建目录，换取检查结果的真实性。
> 代价是 `doctor` 会在首次运行时创建两个空目录——这是可接受且可预期的。
>
> 若需要纯只读诊断，加 `--dry-run` 参数：跳过 D5/D6 的实际创建，只做权限位检查，
> 并在输出中标注「未实际验证」。

### 2.7 `doctor` 与运行模式

`doctor` 报告配置中声明的**运行模式**与**风险接受**。这两项是独立诊断，即使配置文件缺失或损坏，也必须输出 D10、D11；此时它们分别报告 `WARN`，不得让 `doctor` 抛异常。

配置路径与允许值：

| 字段 | 合法值 | 未声明 | 非法值 |
|---|---|---|---|
| `runtime.mode` | `L0` / `L1` / `L2` / `L3` | D10 `WARN` | D4、D10 `FAIL` |
| `risk.acceptance` | `accepted` / `not-accepted` | D11 `WARN` | D4、D11 `FAIL` |

D10 是**工程一致性检查**，不是许可检查：

| 阶段 | 可运行的最高模式 |
|---|---|
| 阶段 1～2 | L3 |
| 阶段 3 | L2 |
| 阶段 4 | L1 |
| 阶段 6 起 | L0 |

阶段 1 中，只有 `runtime.mode = L3` 为 `OK`；声明其他合法模式均为 `FAIL`，因为当前代码尚不具备对应能力。未声明时为 `WARN`，不擅自推断配置值。

D11 在 `risk.acceptance = accepted` 时为 `OK`；未声明或为 `not-accepted` 时为 `WARN`。D11 是风险记录，不作为阶段 1 本地 CLI 的运行许可开关。

**阶段 1 的实现范围**：只校验并报告这两个声明，不连接真实平台、不执行登录或消息操作。

## 3. `status`

### 3.1 作用

回答一个问题：**「现在程序处于什么状态，我下一步该做什么？」**

### 3.2 输出

```
状态：paused_manual
说明：已人工暂停，进程仍在运行（PID 12345，已校验存活）
自：2026-10-23 14:03:11（已暂停 8 分钟）
建议：执行 `dac resume` 恢复，或 `dac stop` 退出

最近事件：
  14:03:11  收到暂停请求
  14:03:14  当前轮结束，进入 paused_manual
```

**「最近事件」的数据来源**：从**日志文件**读取最近 N 条状态变更记录（默认 5 条）。

- 只读日志文件尾部，不额外维护事件存储；
- 读取失败（文件不存在/不可读）时，**省略该段输出**，不报错；
- 只显示 `INFO` 及以上的状态转换事件，不显示 DEBUG。

> `status` 的职责因此是：读状态文件 + 读日志尾部。
> 若日志文件不存在，`status` 仍正常工作（只是没有「最近事件」段）。

**进程已死时的输出**（状态被降级）：

```
状态：stopped
说明：上次进程已退出（PID 12345 不存在），可能是异常终止
      记录的原状态为 paused_manual
自：2026-10-23 14:03:11
建议：执行 `dac run` 重新启动

最近事件：
  14:03:11  收到暂停请求
  14:03:14  当前轮结束，进入 paused_manual
  15:20:02  [status] 检测到 PID 12345 已不存在，降级为 stopped
```

### 3.3 状态与建议的映射

| 状态 | 建议动作 |
|---|---|
| `stopped` | `dac run` |
| `running` | `dac pause` 或 `dac status --watch` |
| `pause_requested` | 等待，通常数秒内转为 `paused_manual` |
| `paused_manual` | `dac resume` 或 `dac stop` |
| `paused_auth` | 重新登录（阶段 3）后 `dac run` |
| `paused_risk` | 人工处理验证后 `dac run` |
| `paused_env` | 检查网络/代理后 `dac run` |
| `paused_unknown` | 人工核对消息后 `dac run` |
| `error` | `dac logs --tail 50` |
| **PID 已死（降级）** | `dac run`（并检查 `dac logs` 确认退出原因） |

> `status` 显示的每个状态都必须经过 PID 存活校验（§5.4）。
> 状态文件里的 `pid` 字段**不可信**，必须实际检查。

### 3.4 退出码

| 情况 | 退出码 | 说明 |
|---|---|---|
| 成功读取状态（含 PID 降级） | `0` | 状态本身不是错误 |
| 状态文件**不存在** | `0` | 视为 `stopped`，输出「尚未运行过」 |
| 状态文件**存在但内容损坏** | `2` | 无法解析，需要人工处理 |

> **「不存在」与「损坏」必须区分**：
> - 不存在 = 全新安装的**正常初始状态**，不是错误；
> - 损坏 = 文件被截断或写了非法内容，**无法判断进程状态**，需要人工介入。
>
> 若把两者都当成错误，全新安装后第一次 `dac status` 就会返回非 0，
> 用户会以为环境有问题。

### 3.5 `status --watch`

| 项 | 定义 |
|---|---|
| 行为 | 每 `status_watch_seconds`（默认 3 秒）重新读取并刷新输出 |
| 刷新方式 | 清屏后重绘，不累积输出 |
| 退出条件 | `Ctrl+C`（退出码 `0`）；状态变为 `stopped` 且原状态非 `stopped` 时**不自动退出**（需人工判断） |
| 与 `pause_poll_seconds` 的关系 | 无关，独立配置 |

> `--watch` 只用于观察，**不修改任何状态**。

## 4. `run`

### 4.1 作用

启动前台运行循环。

### 4.2 阶段 1 的行为

```
0. 读取旧状态文件，执行崩溃恢复判定（见 FAILURE_RULES §4）
     ├─ 文件不存在        → 视为 stopped，继续
     ├─ 内容损坏          → 退出码 1（不覆盖损坏文件，保留现场）
     └─ 状态为 running / pause_requested / paused_manual 且 PID 已死
                          → 记录 WARN，重置为 stopped，继续
   ⚠️ 必须在第 5 步写状态文件之前完成，否则会覆盖崩溃现场
1. 获取单实例锁（失败 → 退出码 4）
2. 加载配置（结构错误 → 退出码 2）
3. 检查运行条件（阶段 1 无必填项；阶段 3 起要求账号/凭证，缺失 → 退出码 3）
4. 写状态文件：running
5. 循环（三种出路，见 MODULE_MAP §4.2）：
     a. 检查控制文件（pause/stop 请求）
     b. 执行一轮「空转」（阶段 1 只记录心跳，不碰抖音）
     c. 本轮结束，按控制意图选择出路：
          ├─ 无请求        → CONTINUE：休眠 cycle_seconds，进入下一轮
          ├─ pause 请求    → SUSPEND：状态转 paused_manual，
          │                  每 pause_poll_seconds 读控制文件
          │                  （resume → 回 CONTINUE；stop → EXIT）
          └─ stop 请求     → EXIT：退出循环
6. 退出时写状态文件
```

> **`SUSPEND` 期间进程存活但不做业务**，这是 `paused_manual` 的定义（§4.4）。
> 信号（`SIGINT` / `SIGTERM`）在挂起期间同样生效，等同 `STOP_IMMEDIATE`（§4.6）。

### 4.3 暂停的精确语义

`pause` 不是立即停止，而是**让当前轮自然结束**：

```
收到 pause 请求
  → 状态写为 pause_requested
  → 当前轮继续执行完
  → 状态写为 paused_manual
  → 循环挂起，等待控制文件变化
```

**为什么不在轮次中间中断**：后续阶段一轮里包含「读消息 → 归档 → 发送」，
中途打断会留下半完成状态。**只在轮次边界检查控制信号**，是保证状态一致的前提。

### 4.4 挂起与恢复的机制

> 这一节定义 `resume` **如何真正唤醒进程**，而不只是改状态字段。

#### 挂起期间的行为

进程进入 `paused_manual` 后，**不退出、不做业务**，只做一件事：**轮询控制文件**。

| 参数 | 值 | 说明 |
|---|---|---|
| 轮询方式 | 轮询 `control.json` 的 mtime | 不依赖 inotify，避免跨文件系统兼容问题 |
| 轮询间隔 | `pause_poll_seconds`，默认 **2 秒** | 独立于 `cycle_seconds`，可配置 |
| 每次轮询动作 | 读 `control.json` → 判断意图 | 不做任何消息/页面操作 |
| 资源占用 | 每 2 秒一次文件 stat，可忽略 | — |

**为什么不用信号**：`CLI_SPEC` §5.1 已规定控制命令只写文件、不操作进程。
挂起进程因此必须主动轮询，这是该设计的必然结果。

#### `resume` 的完整语义

`resume` 不是「把状态改回 running」，而是**一个跨进程握手**：

```
[resume 进程]
  1. 读 state.json，确认状态为 paused_manual
  2. 确认 PID 存活（否则报错，见 §5.4）
  3. 写 control.json: {"intent": "resume", "requested_at": <ts>, "request_id": <uuid>}
  4. 等待 state.json 变为 running（最多等 3 × pause_poll_seconds）
     ├─ 成功 → 输出「已恢复运行」，退出码 0
     └─ 超时 → 输出「恢复请求已写入，但进程未响应」
                + 提示「执行 dac status 查看，或 dac stop 后重新 dac run」
                + 退出码 4（可重试）
```

```
[挂起中的 run 进程]
  1. 每 pause_poll_seconds 读 control.json
  2. 发现 intent=resume 且 request_id 未被消费
  3. 标记 request_id 已消费（写回 control.json）
  4. 状态 paused_manual → running
  5. 回到正常轮次循环，从下一轮开始
```

**关键约束**：

1. `resume` 必须**等待确认**，不能写完文件就报成功——否则用户会以为已恢复。
2. `request_id` 防止重复消费：同一意图只生效一次。
3. 若进程无响应，`resume` 返回退出码 `4`，**不自行 kill 进程**。

#### 不补跑

恢复后从**下一轮**开始，不补跑暂停期间错过的轮次。错过就是错过，不累积。

> 理由：补跑会在短时间内集中发出多条消息，是风控高危行为，也违背「像真人」的产品目标。

### 4.5 暂停期间的资源

| 资源 | 挂起时状态 |
|---|---|
| CPU | 每 2 秒一次 stat，可忽略 |
| 浏览器（阶段 3 起） | **保持打开**（重新打开成本高且可能触发风控） |
| 数据库连接 | 保持 |
| 单实例锁 | **保持持有**（防止暂停时被第二个实例抢占） |

### 4.6 信号处理

| 信号 | 当前状态 | 行为 |
|---|---|---|
| `SIGINT` / `SIGTERM` | `running` / `pause_requested` | 等同 `STOP`：当前轮结束后退出，状态 `stopped`，退出码 `0` |
| `SIGINT` / `SIGTERM` | `paused_manual` | 等同 `STOP_IMMEDIATE`：**立即**退出（无当前轮），状态 `stopped`，退出码 `0` |
| 第二次 `SIGINT` | 任意 | 立即退出，状态 `stopped`，退出码 `0`（用户明确要求强退） |
| `SIGHUP` | 任意 | 忽略（防止终端断开误杀） |

> **挂起期间必须能被信号唤醒**：`SUSPEND` 的轮询循环不能用不可中断的阻塞调用，
> 否则 `Ctrl+C` 会失效。每轮轮询后检查信号标志。
>
> 事件选择依据见 FAILURE_RULES §2 规则 4：有当前轮用 `STOP`，无当前轮用 `STOP_IMMEDIATE`。

### 4.7 退出码（`run`）

| 情况 | 退出码 | 状态 |
|---|---|---|
| 正常停止（`stop` / 信号） | `0` | `stopped` |
| 配置结构错误 | `2` | — |
| 状态文件损坏（第 0 步检测到） | `1` | — |
| 运行条件缺失（**仅阶段 3 起**：无账号/无凭证） | `3` | — |
| 登录失效（阶段 3 起） | `3` | `paused_auth` |
| 单实例锁被占用 | `4` | — |
| 可重试的运行时错误 | `4` | — |
| 不可恢复错误 | `1` | `error` |

## 5. `pause` / `resume` / `stop`

### 5.1 实现方式

三个命令都**不直接操作进程**，只写控制文件；由 `run` 循环读取。

**但 `resume` 额外要求等待确认**（§4.4），因为「写文件」不等于「进程已恢复」。

| 命令 | 写什么 | 前置状态 | 是否等待确认 | 成功退出码 |
|---|---|---|---|---|
| `pause` | `{"intent":"pause", ...}` | 必须是 `running` | 否（异步生效） | `0` = **请求已接受** |
| `resume` | `{"intent":"resume", "request_id":...}` | 必须是 `paused_manual` | **是**（最多 3 × `pause_poll_seconds`） | `0` = **已确认恢复** / `4` = 超时 |
| `stop` | `{"intent":"stop", ...}` | `running` / `paused_manual` / `pause_requested` | 否 | `0` = **请求已接受** |

> **`0` 的含义因命令而异**，必须区分：
>
> | 命令 | `0` 表示 | 不代表 |
> |---|---|---|
> | `pause` | 请求已写入控制文件 | 进程**已经**暂停 |
> | `stop` | 请求已写入控制文件 | 进程**已经**停止 |
> | `resume` | 进程**已经**恢复为 `running` | — |
>
> 初版把退出码 `0` 统一解释为「意图已达成」，对 `pause` / `stop` 是错的——
> 它们只保证「请求被接受」。
>
> **需要确认时**：`pause` / `stop` 之后用 `dac status` 或 `dac status --watch` 观察。
> 不为此增加同步等待，因为等待时长取决于当前轮的长度，不可预测。

**为什么 `pause` 不等待、`resume` 要等待**：

- `pause` 需要等当前轮跑完，轮次长度不定，同步等待会让命令卡住；
- `resume` 只是唤醒挂起进程，最多等一个轮询间隔，等待代价小，而**不等待会让用户误判**。

**状态不匹配时**（如对 `stopped` 执行 `pause`）：

```
错误：当前状态为 stopped，无法 pause。
建议：执行 `dac run` 启动。
```

#### 控制命令的完整退出码

| 情况 | `pause` | `resume` | `stop` |
|---|---|---|---|
| 成功 | `0` | `0`（已确认恢复） | `0` |
| 状态不匹配 | `2` | `2` | `2` |
| 状态文件不存在 | `2`（无实例可暂停） | `2`（无实例可恢复） | `0`（无进程即已停止） |
| 状态文件损坏 | `2` | `2` | `2` |
| PID 已死（状态降级为 `stopped`） | `2` | `2` | `0`（目标已达成） |
| 等待确认超时 | — | `4` | — |
| 控制文件写入失败（权限/磁盘） | `1` | `1` | `1` |

**`stop` 在「进程已死 / 状态文件不存在」时返回 `0` 而非 `2`**：

`stop` 的意图是「确保进程停止」。进程本来就不存在，意图已经达成，不应报错。
这与 `pause` / `resume` 不同——它们要求「进程必须还活着」，进程死了就是**前置条件不满足**。

**判定口径统一为「意图是否达成」，而不是「操作是否执行」**：

| 命令 | 意图 | 已达成的情形 | 未达成的情形 |
|---|---|---|---|
| `pause` | 让运行中的进程暂停 | — | 没有运行中的进程 |
| `resume` | 让挂起的进程恢复 | — | 没有挂起的进程 |
| `stop` | 确保进程不运行 | 进程已死、状态文件不存在 | — |

> 这个区别必须实现正确：运维脚本常写 `dac stop || echo failed`，
> 若进程已死却返回非 0，脚本会误报故障。

**状态文件损坏时的退出码，按「谁在调用」区分**：

| 调用方 | 退出码 | 理由 |
|---|---|---|
| `status` / `pause` / `resume` / `stop` | `2` | 这些是**只读命令**。状态文件坏了，它们无法判断能否执行，属于「调用前置条件不满足」。人工修好文件即可重试 |
| `run` | `1` | `run` 要**接管**这个状态文件。文件损坏意味着持久化层坏了，属于不可恢复错误，需要人工看日志 |

> 为什么不能统一：`run` 遇到损坏文件时，若返回 `2`，systemd 会认为「配置/用法错误」，
> 但实际问题在数据层，日志里才有真相。区分退出码能让运维第一时间找对方向。
>
> 判据是：**命令是否能靠「人工改配置/改状态」解决**。
> 只读命令能（`2`），`run` 不能（`1`）。

### 5.2 控制文件格式

```json
{
  "intent": "resume",
  "request_id": "7c3e9a21",
  "requested_at": "2026-10-23T14:03:11+08:00",
  "consumed_by": null
}
```

| 字段 | 作用 |
|---|---|
| `intent` | `pause` / `resume` / `stop` |
| `request_id` | 幂等键，防止同一意图被重复消费 |
| `requested_at` | 用于 `status` 展示「请求于何时」 |
| `consumed_by` | 被 `run` 消费后写入消费方标识与时间 |

**写入必须原子**：写临时文件 → `os.replace()`。禁止直接覆盖，避免读到半个 JSON。

#### 5.2.1 命令竞争规则

> 单个控制文件意味着后写会覆盖先写。必须定义谁优先。

**优先级（高 → 低）**：`stop` > `resume` > `pause`

**规则**：

| 场景 | 行为 |
|---|---|
| `stop` 已被写入但未被消费，此时 `pause` 写入 | **拒绝** `pause`，返回 `2`，提示「已有 stop 请求待处理」 |
| `stop` 已被写入但未被消费，此时 `resume` 写入 | **拒绝** `resume`，返回 `2`，同上 |
| `pause` 待处理，此时 `resume` 写入 | **允许**：`resume` 覆盖 `pause`（意图反转） |
| `resume` 待处理，此时 `pause` 写入 | **拒绝** `pause`，返回 `2`，提示「恢复请求待处理，请先等待或执行 stop」 |
| 任意状态，`stop` 写入 | **总是允许**：覆盖任何待处理意图 |

**为什么 `stop` 永远优先**：停止是安全动作。任何阻止用户停止进程的规则都是错的。

**为什么 `pause` 不能覆盖 `resume`**：两个意图相反，覆盖会导致状态来回抖动。
若用户真的想再暂停，应等 `resume` 生效后重新 `pause`。

**实现方式**：写入前用**文件锁**保护「读-判断-写」这三步，避免两个 CLI 进程并发写。
这里的锁与 `run.lock` 不同，是 `control.lock`，只保护控制文件本身，粒度极小。

### 5.3 为什么用文件而不是信号

- 信号无法携带语义（`SIGUSR1` 容易被误解释）；
- 文件可被 `status` 读取，形成「状态可观察」的闭环；
- 跨进程重启后控制意图仍在，不会丢失；
- `request_id` 提供幂等性，信号做不到。

> 控制文件放在数据目录下，与状态文件同一处，生命周期一致。

### 5.4 PID 存活校验

状态文件记录 `pid`、`started_at`、`boot_id`、`proc_start_ticks`。**任何命令读取状态时都必须校验**：

```
读取 state.json
  → 状态为 stopped / error          → 直接使用
  → 状态为 running / pause_requested / paused_manual
      → 校验进程身份（三重比对，见下）
          ├─ 全部一致 → 使用记录的状态
          └─ 任一不符 → 降级为 stopped
                        + 标注「上次进程已退出（PID 12345 已不存在或已被复用）」
                        + 记录 WARN 日志
  → 状态为 paused_auth / paused_risk / paused_env / paused_unknown
      → 这些状态本应无进程，若进程身份校验通过 → 标注「状态与进程不一致，请检查」
```

**三重身份校验**（缺一不可）：

| 校验项 | 来源 | 作用 |
|---|---|---|
| `pid` 存在且可 `signal(0)` | `os.kill(pid, 0)` | 排除进程已退出 |
| `boot_id` 相同 | `/proc/sys/kernel/random/boot_id` | 排除「重启后 PID 被复用」 |
| `proc_start_ticks` 相同 | `/proc/<pid>/stat` 第 22 字段 | 排除「同一次开机内 PID 被复用」 |

**为什么不能只看 PID**：PID 会被系统复用。重启后 PID 12345 可能是完全不同的进程；
同一次开机内，前一个进程退出后 PID 也可能被新进程占用。

只看 `signal(0)` 成功就认定「原进程还活着」，会导致：
- `status` 报告假状态；
- `stop` / `pause` 可能对**无关进程**操作。

> 校验函数放在 `infra/state_file.py`，`status` / `run` / `control` 共用，不得各自实现。
> Linux 之外的平台（macOS）缺少 `/proc`，退化为「`boot_id` 用开机时间近似 + 只校验 `pid`」，
> 并在 `doctor` 中标注降级。

### 5.5 锁文件的处理规则

| 事实 | 含义 | 处理 |
|---|---|---|
| 锁文件不存在 | 从未运行或已被清理 | 创建并获取 |
| 锁文件存在，可获取锁 | 上次进程已退出，文件残留 | **复用该文件**，获取锁 |
| 锁文件存在，无法获取锁 | 有实例正在运行 | 退出码 `4` |

**绝不删除锁文件**（原因见 §2.2 D7）。
删除会让后续进程锁住不同的 inode，破坏单实例保证。

## 6. `logs`

### 6.1 用法

```
dac logs                 # 最近 50 行
dac logs --tail 200      # 最近 200 行
dac logs --follow        # 持续跟随
dac logs --level WARN    # 只看 WARN 及以上
```

### 6.2 日志不得包含的内容（硬性）

| 禁止 | 原因 |
|---|---|
| Cookie 值、`sessionid`、`passport_auth_status` | 凭证泄露即账号失守 |
| API Key | 同上 |
| 完整聊天消息正文 | 隐私；日志可能被分享用于排障 |
| 对方昵称全称 | 可关联到真实身份 |

**允许的替代写法**：

```
# ❌
消息内容: 我明天去医院复查，你陪我去吗
# ✅
消息已归档: friend=7f3a2c, len=18, fp=9b1e
```

> 正文只存在于数据库；日志只记**事件与标识**。

### 6.3 日志格式

单行、结构化、可 grep：

```
2026-10-22T14:03:11+0800 INFO  run.cycle       cycle=12 state=running
2026-10-22T14:03:12+0800 INFO  run.pause       pause requested, waiting for cycle boundary
2026-10-22T14:03:14+0800 INFO  run.state       running -> paused_manual
```

## 7. 路径约定

| 项 | 默认值 | 覆盖方式 |
|---|---|---|
| 配置文件 | `./config/config.json` | `--config` |
| 数据目录 | `$XDG_DATA_HOME/dac` 或 `~/.local/share/dac` | `--data-dir` |
| 状态文件 | `<data-dir>/state.json` | — |
| 控制文件 | `<data-dir>/control.json` | — |
| 控制锁文件 | `<data-dir>/control.lock` | — |
| 运行锁文件 | `<data-dir>/run.lock` | — |
| 日志目录 | `<data-dir>/logs/` | — |

### 7.0 相对路径与绝对路径的规则

> 初版既说默认配置文件是 `./config/config.json`（相对），又说「所有路径必须是绝对路径」。
> 这两句不矛盾，但需要说清楚**在哪一步转换**。

| 阶段 | 规则 |
|---|---|
| **输入** | `--config` / `--data-dir` 可以是相对路径，相对于**当前工作目录** |
| **解析后** | 立即转换为绝对路径（`Path.resolve()`），此后**内部只使用绝对路径** |
| **写入状态** | 状态文件、日志中记录的一律是**解析后的绝对路径** |

**为什么**：

- 用户输入相对路径是自然习惯，不该强迫；
- 但程序运行中若工作目录变化（systemd、`cd`、子进程），相对路径会指向错误位置；
- 因此**入口处转换一次，内部永不使用相对路径**。

**诊断输出**：`doctor` 显示解析后的绝对路径，并额外标注原始输入：

```
[OK]   D5 数据目录            /home/user/.local/share/dac
                              （来自默认值；输入为相对路径 ./data 时会显示两者的对应关系）
```

> 状态文件里存绝对路径的代价：数据目录被移动后，旧状态文件里的路径会失效。
> 处理方式：启动时若状态文件记录的 `data_dir` 与当前解析结果不一致，
> 记录 `WARN`，并以**当前路径为准**继续（状态文件本身就在当前数据目录下，不会读错）。

### 7.1 配置字段清单（阶段 1）

> 只列阶段 1 需要的字段。后续阶段新增字段时在此追加，并注明引入阶段。

| 字段 | 类型 | 默认值 | 必填 | 说明 |
|---|---|---|---|---|
| `cycle_seconds` | int | — | **是** | 轮次间隔（秒）。缺失即报错（AC-1.2） |
| `pause_poll_seconds` | int | `2` | 否 | 挂起时轮询控制文件的间隔（§4.4） |
| `status_watch_seconds` | int | `3` | 否 | `status --watch` 的刷新间隔（§3.5） |
| `log_level` | str | `"INFO"` | 否 | 日志级别 |
| `target.douyin_id` | str | `""` | 否 | 目标账号。为空 → D8 `WARN`，`run` 退出码 `3` |
| `login.credentials_file` | str | `""` | 否 | 凭证文件路径。为空或文件不存在 → D9 `WARN` |
| `runtime.mode` | enum | — | 否 | `L0` / `L1` / `L2` / `L3`。未声明 → D10 `WARN`；阶段 1 仅 `L3` 为 `OK` |
| `risk.acceptance` | enum | — | 否 | `accepted` / `not-accepted`。未声明或为 `not-accepted` → D11 `WARN` |

**配置校验规则**：

1. 类型错误 → `ConfigError`，指出字段路径与期望类型；
2. 必填字段缺失 → `ConfigError`；
3. 整数字段 ≤ 0 → `ConfigError`（间隔不能为 0 或负数）；
4. `target`、`login`、`runtime`、`risk` 若存在必须是对象；`runtime.mode` / `risk.acceptance` 若存在，必须属于上表合法值；
5. 未知字段 → **忽略并记 WARN**，不报错（向前兼容）。

> `cycle_seconds` 是唯一必填项。`runtime.mode` / `risk.acceptance` 是可选声明字段，缺失由 D10/D11 分别报告 `WARN`，不导致 D4 失败。

## 8. 退出码总表（AC-1.7）

| 码 | 含义 | 典型场景 | systemd 应否重启 |
|---|---|---|---|
| `0` | 正常 / 请求已接受 | 正常停止、`stop` 时进程已死、状态文件不存在 | 否 |
| `1` | 不可恢复错误 | 写控制文件失败、未捕获异常、`run` 时状态文件损坏 | 否（需人工看日志） |
| `2` | **调用前置条件不满足** | 配置错误、用法错误、状态不匹配、功能未实现、只读命令遇到状态文件损坏 | 否（重启也会同样失败） |
| `3` | 需要人工介入 | 账号/凭证缺失（阶段 3 起）、登录失效、风控、发送结果未知 | **否**（否则反复撞同一问题） |
| `4` | 可重试错误 | **启动时**锁被占用、`resume` 超时 | 是 |

**重要：退出码只描述「进程退出」的结果。**

| 进程 | 退出码的含义 |
|---|---|
| `run`（服务主进程） | systemd 依据它决定是否重启 |
| `pause` / `resume` / `stop`（一次性 CLI 调用） | 只对**调用者**有意义，**systemd 看不到** |

> 初版把「临时网络错误」列为退出码 `4` 的典型场景，与 `FAILURE_RULES` F7b 冲突。
> 修正：运行期网络错误在进程内重试，**不退出**，因此**没有退出码**。
> 只有启动期锁冲突和 `resume` 超时会让进程以 `4` 退出。

**`2` 的定义为什么是「调用前置条件不满足」**：

初版写作「配置错误 / 命令用法错误」，但实际还要覆盖：
状态不匹配（对 `stopped` 执行 `pause`）、功能未实现（阶段 1 的 `login`）。

这些场景的共同点是：**命令本身没错，是当前环境/状态不允许执行它**。
统一归入 `2`，避免为每种情况发明新退出码。

> 这个表是阶段 7 systemd 配置的唯一依据。阶段 1 必须严格实现，不能事后补。
