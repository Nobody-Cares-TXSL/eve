## 2. `doctor`（已实现）

### 2.1 作用

回答一个问题：**「这台机器现在能不能跑这个程序？」**
逐项检查，每项独立报告，不因为一项失败就中断。

### 2.2 检查项

| 编号 | 检查 | 通过条件 | 失败级别 |
|---|---|---|---|
| D1 | Python 版本 | ≥ 3.11 | `FAIL` |
| D2 | 依赖可用 | `playwright`、`httpx` 可导入 | `WARN`（阶段 1）→ `FAIL`（阶段 3 起） |
| D3 | 模块命名 | **`src/` 下**无 `.py` 文件名与 `sys.stdlib_module_names` 冲突 | `FAIL` |
| D4 | 配置结构 | 配置文件存在且字段合法 | `FAIL`（存在未知字段时可 `WARN`） |
| D5 | 数据目录 | 目录**已存在且可写**，或可创建 | `FAIL` |
| D6 | 日志目录 | 目录**已存在且可写**，或可创建 | `FAIL` |
| D7 | 单实例锁 | 无其他实例占用；只读探测，不获取锁 | `WARN`（发现占用或残留锁文件时） |
| D8 | 目标账号 | `target.douyin_id` 已填写 | `WARN`（未配置） |
| D9 | 登录凭证 | `login.credentials_file` 指向存在的文件 | `WARN`（未配置或文件不存在） |
| D10 | 运行模式 | `runtime.mode` 是合法模式，且不超过当前工程阶段上限 | `FAIL`（非法或超过上限）；`WARN`（未声明） |
| D11 | 风险接受 | `risk.acceptance` 已声明为 `accepted` | `WARN`（未声明或为 `not-accepted`） |

**级别语义**：

- `FAIL`：阻塞 `run`，`doctor` 退出码 `2`
- `WARN`：不阻塞 `doctor`，但可能阻塞 `run`（属于「运行条件缺失」或「阶段未到」）
- `OK`：通过

> **D2 在阶段 1 为 `WARN`**：`playwright` / `httpx` 阶段 3 才真正需要，
> 阶段 1 检测它们只是「提前告知」，不应阻塞骨架开发。阶段 3 起升为 `FAIL`。
>
> **D8/D9 为 `WARN`**，依据 D-007：**配置校验与运行条件分离**。
> 阶段 1 尚未填写目标账号时，`doctor` 仍应能完整跑完。

#### D3 的扫描范围（防止误报）

```
扫描根：<repo>/src/
递归：是
包含：所有 *.py
排除：以 .gitignore 匹配的路径
排除：__pycache__、.venv、venv
判定：文件 stem（不含 .py）∈ sys.stdlib_module_names → FAIL
```

**为什么必须限定范围**：仓库根目录下有 `douyin-bot/`、`douyin-robot/` 两个参考项目，
其中 `douyin-robot/src/selectors.py` 与标准库同名。若全仓库扫描，`doctor` 会永远报 `FAIL`，
而那个文件**不属于本项目**，也不参与运行。

> 实现必须与 `.gitignore` 保持一致：被忽略的目录不扫描。
> 若 `.gitignore` 缺失，退化为只扫 `src/`。

#### D5 / D6 的判定顺序

```
1. 目录不存在 → 尝试创建
     ├─ 创建成功且可写 → OK
     └─ 创建失败 → FAIL（附具体 errno）
2. 目录已存在
     ├─ 可写 → OK
     └─ 不可写 → FAIL（附路径与权限说明）
```

**不能只测「能否创建」**：目录已存在但只读是最典型的权限故障，必须单独覆盖。

#### D7 的检测方式

`doctor` **只读探测，不获取锁**。

```
1. 锁文件不存在 → OK
2. 锁文件存在
     ├─ 尝试以「非阻塞」方式获取锁（flock LOCK_EX | LOCK_NB）
     │    ├─ 获取成功 → 立即释放 → WARN「锁文件存在但无人持有（上次未清理，run 会复用）」
     │    └─ 获取失败 → WARN「已有实例在运行」
```

**关键规则**：

1. **绝不删除锁文件。** 对 `flock` 而言，文件存在 ≠ 锁被持有。
   删除文件会让后续进程锁住**不同的 inode**，两个实例同时「持有锁」，单实例保证失效。
2. **「锁文件存在」与「锁被占用」是两个不同的事实**，必须分开报告。
3. `doctor` 获取锁后**立即释放**，不做任何业务。
4. 探测必须用非阻塞模式（`LOCK_NB`），否则会卡住。

> 这条规则同样适用于 `run`：`run` 启动时若锁文件存在但无人持有，
> **直接复用该文件**，不删除、不重建。

### 2.3 输出格式

人类可读的表格，每行一项：

**场景一：干净目录，配置缺失**（实际运行输出）

```
[OK]   D1  Python 版本      3.12.3 (要求 >= 3.11)
[WARN] D2  依赖可用         缺少 playwright、httpx（阶段 1 暂不阻塞）
[OK]   D3  模块命名         无标准库同名模块
[FAIL] D4  配置结构         配置文件不存在：/path/to/config.json
                            → 修复：按 docs/CLI_SPEC.md §3.2 创建配置，并填写必需字段 cycle_seconds
[OK]   D5  数据目录         /path/to/data
[OK]   D6  日志目录         /path/to/data/logs
[OK]   D7  单实例锁         未发现运行锁文件
[WARN] D8  目标账号         配置不可用，未检查目标账号（见 D4）
[WARN] D9  登录凭证         配置不可用，未检查登录凭证（见 D4）
[WARN] D10 运行模式         配置不可用，未检查 runtime.mode（见 D4）
[WARN] D11 风险接受         配置不可用，未检查 risk.acceptance（见 D4）

结论：1 项 FAIL、5 项 WARN、5 项 OK；doctor 退出码 2。
```

**场景二：配置合法但可选字段未填**

D4 为 `OK`；D8/D9 报「未配置…（阶段 3 前无需填写）」；D10/D11 报「未声明…」。
四项均为 `WARN`，退出码 `0`。

| 情况 | 退出码 |
|---|---|
| 全部 `OK` 或仅 `WARN` | `0` |
| 存在 `FAIL` | `2` |

### 2.5 `--json`

输出机器可读 JSON，供测试断言使用：

```json
{
  "checks": [
    {"id": "D1", "level": "ok", "detail": "3.12.3 (要求 >= 3.11)"},
    {"id": "D2", "level": "warn", "detail": "缺少 playwright、httpx（阶段 1 暂不阻塞）", "fix": "阶段 3 起安装 requirements.txt"},
    {"id": "D3", "level": "ok", "detail": "无标准库同名模块"},
    {"id": "D4", "level": "fail", "detail": "配置文件不存在：/path/to/config.json", "fix": "按 docs/CLI_SPEC.md §3.2 创建配置，并填写必需字段 cycle_seconds"},
    {"id": "D5", "level": "ok", "detail": "/path/to/data"},
    {"id": "D6", "level": "ok", "detail": "/path/to/data/logs"},
    {"id": "D7", "level": "ok", "detail": "未发现运行锁文件"},
    {"id": "D8", "level": "warn", "detail": "配置不可用，未检查目标账号（见 D4）"},
    {"id": "D9", "level": "warn", "detail": "配置不可用，未检查登录凭证（见 D4）"},
    {"id": "D10", "level": "warn", "detail": "配置不可用，未检查 runtime.mode（见 D4）"},
    {"id": "D11", "level": "warn", "detail": "配置不可用，未检查 risk.acceptance（见 D4）"}
  ],
  "summary": {"fail": 1, "warn": 5, "ok": 5}
}
```

**JSON 契约（测试依赖）**：

| 项 | 保证 |
|---|---|
| `checks` 顺序 | 严格 `D1` → `D11`，共 11 项，不增不减 |
| `checks[].id` | `D1`…`D11` |
| `checks[].level` | `ok` / `warn` / `fail` |
| `checks[].detail` | 非空字符串 |
| `checks[].fix` | 仅在有修复建议时出现，可为空 |
| `summary` | 三个键 `fail` / `warn` / `ok`，各自计数**必须**与 `checks` 逐条统计一致 |

> 配置缺失或损坏时，D8～D11 **仍然输出**，内容为「配置不可用，未检查…（见 D4）」，
> 级别为 `warn`——不得因 D4 失败而让这四项消失或抛异常。

> AC-1.1、AC-1.2、AC-1.3 的自动化测试**只依赖 `--json`**，不解析人类可读输出。

### 2.6 `doctor` 的副作用边界

> 初版称 `doctor` 为「只读」，但 D5/D6 又要尝试创建目录——自相矛盾。
> 这里明确允许的副作用范围。

**`doctor` 允许的副作用（仅此一项）**：

| 允许 | 说明 |
|---|---|
| 创建数据目录、日志目录 | 为了验证「能否创建」，必须真的尝试 |

**`doctor` 禁止的副作用**：

| 禁止 | 原因 |
|---|---|
| 写状态文件、控制文件 | 会干扰正在运行的实例 |
| 获取单实例锁 | 会阻塞 `run` |
| 写日志文件 | `doctor` 结果只打到 stdout，不写日志文件（排障时用户自行重定向） |
| 创建配置文件 | 只报告缺失，不代替用户做决定 |
| 删除任何文件（含残留锁） | 见 §2.2 D7 与 §3.5 |

**为什么不干脆禁止创建目录**：

D5/D6 的检查目的是「`run` 时能不能用」。若只检查父目录权限而不实际创建，
会漏掉「父目录可写但同名文件已存在」「磁盘满」等情况。

> **权衡**：允许创建目录，换取检查结果的真实性。
> 代价是 `doctor` 会在首次运行时创建两个空目录——这是可接受且可预期的。
>
> 若需要纯只读诊断，加 `--dry-run` 参数：跳过 D5/D6 的实际创建，只做权限位检查，
> 并在输出中标注「未实际验证」。

### 2.7 `doctor` 与运行模式

`doctor` 报告配置中声明的**运行模式**与**风险接受**。这两项是独立诊断，即使配置文件缺失或损坏，也必须输出 D10、D11；此时它们分别报告 `WARN`，不得让 `doctor` 抛异常。

配置路径与允许值：

| 字段 | 合法值 | 未声明 | 非法值 |
|---|---|---|---|
| `runtime.mode` | `L0` / `L1` / `L2` / `L3` | D10 `WARN` | D4、D10 `FAIL` |
| `risk.acceptance` | `accepted` / `not-accepted` | D11 `WARN` | D4、D11 `FAIL` |

D10 是**工程一致性检查**，不是许可检查：

| 阶段 | 可运行的最高模式 |
|---|---|
| 阶段 1～2 | L3 |
| 阶段 3 | L2 |
| 阶段 4 | L0（首次真实发送期建议暂用 L1 验收门，见 D-015） |
| 阶段 6 起 | L0（含主动聊天） |

阶段 1 中，只有 `runtime.mode = L3` 为 `OK`；声明其他合法模式均为 `FAIL`，因为当前代码尚不具备对应能力。未声明时为 `WARN`，不擅自推断配置值。

D11 在 `risk.acceptance = accepted` 时为 `OK`；未声明或为 `not-accepted` 时为 `WARN`。D11 是风险记录，不作为阶段 1 本地 CLI 的运行许可开关。

**阶段 1 的实现范围**：只校验并报告这两个声明，不连接真实平台、不执行登录或消息操作。

## 3. 路径与配置

| 项 | 默认值 | 覆盖方式 |
|---|---|---|
| 配置文件 | `./config/config.json` | `--config` |
| 数据目录 | `$XDG_DATA_HOME/dac` 或 `~/.local/share/dac` | `--data-dir` |
| 状态文件 | `<data-dir>/state.json` | — |
| 控制文件 | `<data-dir>/control.json` | — |
| 控制锁文件 | `<data-dir>/control.lock` | — |
| 运行锁文件 | `<data-dir>/run.lock` | — |
| 日志目录 | `<data-dir>/logs/` | — |

### 3.1 相对路径与绝对路径的规则

> 初版既说默认配置文件是 `./config/config.json`（相对），又说「所有路径必须是绝对路径」。
> 这两句不矛盾，但需要说清楚**在哪一步转换**。

| 阶段 | 规则 |
|---|---|
| **输入** | `--config` / `--data-dir` 可以是相对路径，相对于**当前工作目录** |
| **解析后** | 立即转换为绝对路径（`Path.resolve()`），此后**内部只使用绝对路径** |
| **写入状态** | 状态文件、日志中记录的一律是**解析后的绝对路径** |

**为什么**：

- 用户输入相对路径是自然习惯，不该强迫；
- 但程序运行中若工作目录变化（systemd、`cd`、子进程），相对路径会指向错误位置；
- 因此**入口处转换一次，内部永不使用相对路径**。

**诊断输出**：`doctor` 显示解析后的绝对路径，并额外标注原始输入：

```
[OK]   D5 数据目录            /home/user/.local/share/dac
                              （来自默认值；输入为相对路径 ./data 时会显示两者的对应关系）
```

> 状态文件里存绝对路径的代价：数据目录被移动后，旧状态文件里的路径会失效。
> 处理方式：启动时若状态文件记录的 `data_dir` 与当前解析结果不一致，
> 记录 `WARN`，并以**当前路径为准**继续（状态文件本身就在当前数据目录下，不会读错）。

### 3.2 配置字段清单（阶段 1）

> 只列阶段 1 需要的字段。后续阶段新增字段时在此追加，并注明引入阶段。

| 字段 | 类型 | 默认值 | 必填 | 说明 |
|---|---|---|---|---|
| `cycle_seconds` | int | — | **是** | 轮次间隔（秒）。缺失即报错（AC-1.2） |
| `pause_poll_seconds` | int | `2` | 否 | 挂起时轮询控制文件的间隔（§4.2） |
| `status_watch_seconds` | int | `3` | 否 | `status --watch` 的刷新间隔（§4.1） |
| `log_level` | str | `"INFO"` | 否 | 日志级别 |
| `target.douyin_id` | str | `""` | 否 | 目标账号。为空 → D8 `WARN`，`run` 退出码 `3` |
| `login.credentials_file` | str | `""` | 否 | 凭证文件路径。为空或文件不存在 → D9 `WARN` |
| `runtime.mode` | enum | — | 否 | `L0` / `L1` / `L2` / `L3`。未声明 → D10 `WARN`；阶段 1 仅 `L3` 为 `OK` |
| `risk.acceptance` | enum | — | 否 | `accepted` / `not-accepted`。未声明或为 `not-accepted` → D11 `WARN` |

**配置校验规则**：

1. 类型错误 → `ConfigError`，指出字段路径与期望类型；
2. 必填字段缺失 → `ConfigError`；
3. 整数字段 ≤ 0 → `ConfigError`（间隔不能为 0 或负数）；
4. `target`、`login`、`runtime`、`risk` 若存在必须是对象；`runtime.mode` / `risk.acceptance` 若存在，必须属于上表合法值；
5. 未知字段 → **忽略并记 WARN**，不报错（向前兼容）。

> `cycle_seconds` 是唯一必填项。`runtime.mode` / `risk.acceptance` 是可选声明字段，缺失由 D10/D11 分别报告 `WARN`，不导致 D4 失败。

## 4. 未实现命令（摘要）

> 以下只记录**必须现在就定、否则会导错实现**的约束。完整规格在实现前补写。

### 4.1 `status`

读取状态文件，输出状态 + 建议动作。**读状态时必须校验进程身份**（pid + boot_id + proc_start_ticks），
PID 已死则降级为 `stopped`。

状态文件不存在 → 退出码 `0`（视为 `stopped`，全新安装的正常状态）；
内容损坏 → 退出码 `2`。

### 4.2 `run`

启动顺序（**状态恢复必须在写状态文件之前**）：

```
0. 读旧状态，执行崩溃恢复判定
1. 获取单实例锁（失败 → 4）
2. 加载配置（结构错误 → 2）
3. 检查运行条件（阶段 3 起才要求账号/凭证，缺失 → 3）
4. 写状态文件：running
5. 循环（三态：CONTINUE / SUSPEND / EXIT）
6. 退出时写状态文件
```

**`SUSPEND` 是 `paused_manual` 的实现**：进程存活但不做业务，每 `pause_poll_seconds` 读控制文件。

### 4.3 `pause` / `resume` / `stop`

只写控制文件，不操作进程。控制文件格式：

```json
{"intent": "resume", "request_id": "7c3e9a21", "requested_at": "...", "consumed_by": null}
```

**竞争规则**：`stop` > `resume` > `pause`。`stop` 总是允许，其余按优先级拒绝。

**等待语义**：`pause` / `stop` 不等待（退出码 `0` = 请求已接受）；
`resume` 等待确认（`0` = 已恢复，`4` = 超时）。

### 4.4 `logs`

`--tail N` / `--follow` / `--level`。日志**不得包含** Cookie、API Key、聊天正文、对方昵称全称。

### 4.5 状态与语义

| 状态 | 进程存活 | 恢复方式 |
|---|---|---|
| `stopped` | ❌ | `run` |
| `running` | ✅ | — |
| `pause_requested` | ✅ | 等待自动转 `paused_manual` |
| `paused_manual` | ✅ | `resume` |
| `paused_auth` / `paused_risk` / `paused_env` / `paused_unknown` | ❌ | 人工处理后 `run` |
| `error` | ❌ | 看日志 |

**关键**：`paused_manual` 进程存活，其余 `paused_*` 进程退出。

## 5. 退出码总表（AC-1.7）

| 码 | 含义 | 典型场景 | systemd 应否重启 |
|---|---|---|---|
| `0` | 正常 / 请求已接受 | 正常停止、`stop` 时进程已死、状态文件不存在 | 否 |
| `1` | 不可恢复错误 | 写控制文件失败、未捕获异常、`run` 时状态文件损坏 | 否（需人工看日志） |
| `2` | **调用前置条件不满足** | 配置错误、用法错误、状态不匹配、功能未实现、只读命令遇到状态文件损坏 | 否（重启也会同样失败） |
| `3` | 需要人工介入 | 账号/凭证缺失（阶段 3 起）、登录失效、风控、发送结果未知 | **否**（否则反复撞同一问题） |
| `4` | 可重试错误 | **启动时**锁被占用、`resume` 超时 | 是 |

**重要：退出码只描述「进程退出」的结果。**

| 进程 | 退出码的含义 |
|---|---|
| `run`（服务主进程） | systemd 依据它决定是否重启 |
| `pause` / `resume` / `stop`（一次性 CLI 调用） | 只对**调用者**有意义，**systemd 看不到** |

> 初版把「临时网络错误」列为退出码 `4` 的典型场景，与 `FAILURE_RULES` F7b 冲突。
> 修正：运行期网络错误在进程内重试，**不退出**，因此**没有退出码**。
> 只有启动期锁冲突和 `resume` 超时会让进程以 `4` 退出。

**`2` 的定义为什么是「调用前置条件不满足」**：

初版写作「配置错误 / 命令用法错误」，但实际还要覆盖：
状态不匹配（对 `stopped` 执行 `pause`）、功能未实现（阶段 1 的 `login`）。

这些场景的共同点是：**命令本身没错，是当前环境/状态不允许执行它**。
统一归入 `2`，避免为每种情况发明新退出码。

> 这个表是阶段 7 systemd 配置的唯一依据。阶段 1 必须严格实现，不能事后补。
