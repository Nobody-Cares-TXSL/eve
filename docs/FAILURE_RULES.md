## 0. 核心原则

1. **失败即停**：无法确认安全时暂停，不重试。
2. **状态显式**：任何故障都必须落到一个**已定义的状态**，不允许「进程挂了但说不清为什么」。
3. **退出码即契约**：systemd 只看退出码。码不对，运维就错。
4. **未知 ≠ 失败**：`unknown` 是独立状态，不能归入 `failed`。

## 2. 状态转换表

> `—` 表示该状态不因这个事件改变。`✗` 表示非法转换，必须报错。

| 当前状态 ↓ / 事件 → | `START` | `PAUSE` | `RESUME` | `STOP` | `STOP_IMMEDIATE` | `CYCLE_END` | `AUTH_LOST` | `FATAL` |
|---|---|---|---|---|---|---|---|---|
| `stopped` | `running` | ✗ | ✗ | — | — | — | — | — |
| `running` | ✗ | `pause_requested` | ✗ | `stopped` | ✗ | — | `paused_auth` | `error` |
| `pause_requested` | ✗ | — | ✗ | `stopped` | ✗ | `paused_manual` | `paused_auth` | `error` |
| `paused_manual` | ✗ | — | `running` | — | `stopped` | — | — | `error` |
| `paused_auth` | ✗ | ✗ | ✗ | — | — | — | — | — |
| `paused_risk` | ✗ | ✗ | ✗ | — | — | — | — | — |
| `paused_env` | ✗ | ✗ | ✗ | — | — | — | — | — |
| `paused_unknown` | ✗ | ✗ | ✗ | — | — | — | — | — |
| `error` | ✗ | ✗ | ✗ | — | — | — | — | — |

**关键规则**：

1. **`paused_auth` / `paused_risk` / `paused_env` / `paused_unknown` 是终态**（对本进程而言）。
   它们表示「进程即将退出，等人工介入」，只能通过重新 `run` 离开。
2. **`paused_manual` 不是终态**，可通过 `RESUME` 回到 `running`。
3. **`stopped` 只能通过 `START` 离开**，不能 `RESUME`。
4. **`STOP` 与 `STOP_IMMEDIATE` 按「是否有当前轮」区分**：
   - `running` / `pause_requested` 有当前轮 → 用 `STOP`，等轮次结束；
   - `paused_manual` 无当前轮 → 用 `STOP_IMMEDIATE`，立即退出。
   - 反之均为**非法转换**：`running + STOP_IMMEDIATE` 会破坏「只在轮次边界改状态」；
     `paused_manual + STOP` 会让挂起进程去等一个不存在的轮次。

> 事件定义见 MODULE_MAP §4.1。状态机是纯函数，它不知道进程当前是否在轮次中，
> 因此必须由调用方选择正确的事件——**这是事件拆分的唯一目的**。

## 3. 各故障的完整处理流程

### F1 配置错误

```
加载配置
  → 字段缺失 / 类型错误
  → 记录日志（含字段路径，不含值）
  → 输出：
      配置错误：runtime.cycle_seconds 缺失
      修复：在 config/config.json 中添加 "cycle_seconds": 30
  → 退出码 2
```

**不做的事**：不使用默认值继续运行。

> 依据 SOURCE_AUDIT §2.2：`douyin-robot` 因静默默认值，轮询间隔变成 1 秒。

---

### F2 运行条件缺失

```
doctor 通过结构校验
  → run 检查运行条件
  → target.douyin_id 为空
  → 输出：
      无法启动：尚未配置目标账号。
      说明：阶段 3 前无需填写；填写后即可运行。
      字段：target.douyin_id
  → 退出码 3
```

**`doctor` 不因此失败**（D-007）。

---

### F3 登录失效

```
运行中检测到凭证失效（阶段 3 起；阶段 1 用注入故障模拟）
  → 状态：running → paused_auth
  → 写状态文件（持久化，重启后仍可见）
  → 日志：ERROR auth lost, entering paused_auth
  → 退出码 3
```

**为什么退出而不是挂着等**：

- 挂着等会占用浏览器资源，且 systemd 看不到「需要人工」的信号；
- 退出码 `3` 让 systemd 明确「不要重启」；
- 状态文件保留 `paused_auth`，`status` 能告诉用户下一步该做什么。

---

### F4 平台风控

同 F3，状态为 `paused_risk`。

**不做的事**：

- ❌ 不自动重试
- ❌ 不尝试过验证
- ❌ 不切换 IP / UA

> 这是 PRD §2.1 的硬性边界。

---

### F5 结果未知（阶段 4）

```
发送后确认超时
  → 状态：paused_unknown
  → 记录：incoming_fp、拟发送内容哈希、尝试时间
  → 退出码 3
```

**绝不自动重试**（D-004）。人工核对后重新 `run`。

---

### F6 人工暂停

```
收到 pause 请求
  → 状态：running → pause_requested
  → 当前轮执行完毕（不中断）
  → 状态：pause_requested → paused_manual
  → 进程保持存活，等待 resume
```

**关键**：只在**轮次边界**检查控制信号。中途不打断。

> 原因：后续阶段一轮内含「读→归档→发送」，中途打断会留下半完成状态。

---

### F7 可重试错误（启动期）

```
启动时尝试获取单实例锁
  → 锁被占用
  → 输出：已有实例在运行（PID xxx），本次启动取消
  → 退出码 4
```

**为什么是 `4` 而不是 `3`**：这不是「需要人工介入」——前一个实例正常退出后，
再次 `run` 就能成功。systemd 应当重启（`RestartSec=30`），不应永久放弃。

> 注意：这里**不做退避重试**。进程直接退出，把重试交给 systemd，
> 避免两个实例在锁上互相等待。

---

### F7b 可重试错误（运行期）

```
运行时错误（如页面未加载完、临时网络故障）
  → 指数退避重试（1s, 2s, 4s，最多 3 次）
  → 3 次仍失败
      → 计入连续失败计数
      → 达到阈值（默认 5）→ 状态 paused_env，退出码 3
      → 未达阈值 → 继续下一轮
```

**进程本身不退出**，除非达到阈值。因此**重试阶段没有退出码**——
「退出码」只在进程真正退出时才有意义。

#### F7c 重试耗尽后进入 `paused_env`，不是 `paused_risk`

| 状态 | 触发原因 | 恢复动作 |
|---|---|---|
| `paused_env` | 网络不可用、页面持续加载失败 | 检查网络/代理，修复后 `run` |
| `paused_risk` | 验证码、安全验证、滑块 | **人工完成验证**后 `run` |

**为什么必须分开**：

- 恢复动作不同：网络问题重试可能自愈，风控必须人工介入；
- 归因不同：把网络故障记成「风控」会误导排查方向；
- 计数策略不同：网络故障可以较频繁重试，风控必须长时间退避。

> `paused_env` 由阶段 3 引入（阶段 1 没有网络与页面）。阶段 1 只在状态枚举中**预留**该值，
> 不实现产生它的逻辑。

---

### F8 不可恢复错误

```
未捕获异常
  → 状态：error
  → 日志：完整 traceback（脱敏后）
  → 保存故障现场（阶段 3 起：截图 + HTML）
  → 退出码 1
```

## 4. 进程崩溃与恢复

### F9 崩溃后的启动自检

```
启动
  → 读取状态文件，校验 pid 存活（CLI_SPEC §5.4）
  → 状态为 running / pause_requested / paused_manual
      → 这三者的定义都要求「进程存活」
      → 能走到这一步说明进程已死（否则会撞单实例锁）
      → 记录 WARN：检测到上次非正常退出（状态=<旧状态>，pid=<旧pid> 已不存在）
      → 状态重置为 stopped
      → 继续正常启动流程
  → 状态为 paused_auth / paused_risk / paused_env / paused_unknown
      → 这三个状态的定义是「进程已退出，等人工介入」
      → 保持原状态，提示用户下一步
  → 状态文件不存在
      → 视为 stopped（全新安装的正常初始状态，不是错误）
      → 不记录 WARN，不报错
  → 状态文件存在但内容损坏
      → 视为 stopped，记录 WARN
      → 退出码按调用方区分（CLI_SPEC §5.1）：
          ├─ 只读命令（status / pause / resume / stop）→ 退出码 2
          └─ run（要接管状态文件）                    → 退出码 1
```

**为什么 `paused_manual` 归入「重置为 stopped」**：

`paused_manual` 的语义是**进程存活、挂起等待 resume**（ARCHITECTURE §8）。
启动时读到它，只可能是进程已经死了却来不及改状态——**它不可能是「预期退出」**。
若保持原状态，`status` 会报告「进程仍在运行（PID xxx）」，而那个 PID 可能已被系统复用。

**不做的**：不尝试「猜测」崩溃前在做什么。状态文件只记**结果**，不记**过程**。

> 阶段 2 引入归档游标后，才需要「从游标恢复」的复杂逻辑。
> 阶段 1 的恢复就是「重置为 stopped」。

## 5. 日志脱敏规则（硬性）

### 5.1 禁止出现的字段

| 字段 | 正则/键名 |
|---|---|
| Cookie 值 | `sessionid`、`sessionid_ss`、`sid_guard`、`passport_auth_status`、`uid_tt`、`ttwid`、`odin_tt` |
| API Key | `api_key`、`Authorization`、`Bearer *`、`sk-*` |
| 聊天正文 | 任何消息 `content` / `text` 字段 |
| 对方昵称 | 完整昵称（可用哈希前 6 位代替） |

### 5.2 实现方式

```python
# infra/log_setup.py
class RedactFilter(logging.Filter):
    """在 handler 层脱敏。即使调用方误传敏感内容，也不会落盘。"""
```

**在 handler 层而不是调用层做脱敏**——调用层总会有人忘记。

### 5.3 允许记录的替代形式

| 原值 | 记录为 |
|---|---|
| 消息正文 | `len=18 fp=9b1e2c` |
| 昵称 | `friend=7f3a2c` |
| Cookie | 不记录，或 `cookie_count=12` |
| API Key | `api_key=set` / `api_key=unset` |

## 6. systemd 交互（阶段 7 的输入）

| 退出码 | systemd 行为 |
|---|---|
| `0` | 不重启 |
| `1` | 不重启（`Restart=on-failure` 会重启，需用 `RestartPreventExitStatus=1 2 3`） |
| `2` | 不重启 |
| `3` | **不重启**（关键：否则反复撞同一问题） |
| `4` | 重启（`RestartSec=30`） |

**退出码的适用主体**：

| 进程 | systemd 是否观察其退出码 |
|---|---|
| `run`（服务主进程） | ✅ 是 —— 这是唯一影响重启策略的退出码 |
| `pause` / `resume` / `stop`（一次性调用） | ❌ 否 —— 它们不注册为服务，systemd 看不到 |

> 初版在 `CLI_SPEC §8` 暗示「`resume` 超时的退出码 `4` 会让 systemd 重启」——这是错的。
> `resume` 是一次性命令，它的退出码只对调用者（人或脚本）有意义。
> **只有 `run` 的退出码参与 systemd 决策。**

**阶段 1 必须保证**：退出码严格按此表。
阶段 7 的 service 文件会写：

```ini
Restart=on-failure
RestartPreventExitStatus=1 2 3
```

> 若阶段 1 的退出码错了，阶段 7 无论怎么配都救不回来。

## 7. 故障处理检查清单

任何故障处理实现完成后，逐条确认：

- [ ] 故障落到**已定义**的状态，不是「崩溃」
- [ ] 退出码符合 §1 的表
- [ ] 状态文件已持久化（重启后 `status` 能读到）
- [ ] 日志含**原因**，不含**敏感值**
- [ ] 有对应的自动化测试
- [ ] 你能讲出「这个故障发生后，进程做了什么、为什么」——Understanding Gate
