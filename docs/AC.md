# 验收条件 — AC

> 版本：v1.2
> 状态：阶段 0 交付物（待确认）
> 范围：**仅阶段 0～2**。阶段 3 之后的 AC 在对应阶段启动前定义，不提前写。
> 规则：AC 一经确认，不得为了通过测试而修改。发现不合理必须先记录变更原因。

---

## 使用方式

每条 AC 包含四个字段：

- **条件**：可观察的期望行为
- **证据**：什么能证明它成立（必须是可重复执行的）
- **失败状态**：不满足时系统处于什么状态
- **类型**：`自动测试` / `人工检查` / `证据记录`

「证据」不能是「看起来正常」，必须是命令输出、测试结果或文件。

# 阶段 0：项目定义与可行性关口

## AC-0.1 文档齐备

| 项 | 内容 |
|---|---|
| 条件 | `docs/PRD.md`、`docs/SOURCE_AUDIT.md`、`docs/ARCHITECTURE.md`、`docs/AC.md`、`docs/DECISIONS.md` **五份**文件存在，且每份**要么**头部有「审查记录」小节、**要么**在 `docs/REVIEWS.md` 中有对应条目 |

## AC-0.1c 文档确认不得先于内容审查

| 项 | 内容 |
|---|---|
| 条件 | 每份文档标记「已确认」前，必须先完成一次只读审查，且审查记录中每条问题都有明确结论（已修复 / 接受 / 拒绝并说明理由） |
| 证据 | 审查结论写在文档头部的「审查记录」小节，包含日期、审查范围、问题清单与处置 |

| 类型 | 人工检查 |

## AC-0.2 源码审计结论有证据支撑

| 项 | 内容 |
|---|---|
| 条件 | SOURCE_AUDIT 中每条 P0/P1 结论**要么可复现**（附命令与输出），**要么明确标注为「静态代码审查，未运行验证」** |
| 证据 | ① 运行类结论逐条可复现（见下表）；② 静态类结论在 SOURCE_AUDIT 中标注证据类型；③ 无「既不可复现、又未标注」的结论 |
| 失败状态 | 未标注的结论降级为「推测」，不得作为设计输入 |
| 类型 | 证据记录 |

**运行类结论的复现证据**：

| 结论 | 复现命令 | 预期 |
|---|---|---|
| `selectors` 命名冲突 | `python3 douyin-robot/src/main.py --help` | `AttributeError: module 'selectors' has no attribute 'SelectSelector'` |
| 轮询间隔失效 | `_random_range({'cycle_min_seconds':15,'cycle_max_seconds':35})` | 返回约 1 秒，而非 15–35 |
| 日限额未生效 | `rg 'replied_at_day' douyin-robot/src/` | 只有读取（`reply_engine.py:85`），无写入 |
| SQLite 连接未关闭 | `with sqlite3.connect(':memory:') as c: pass` 后调用 `c.execute` | 成功执行 → 连接未关闭 |

**静态类结论**（代码审查，未运行验证，SOURCE_AUDIT 中已标注）：

| 结论 | 依据 |
|---|---|
| 昵称子串匹配可串话 | `douyin-bot/bot_manager.py:344` 使用 `innerText.includes(nickname)` |
| 物理坐标硬编码脆弱 | `douyin-bot/bot_manager.py:292` 等处的固定 `x/y` |
| 文本哈希无法区分同文异事件 | `douyin-robot/src/reply_engine.py:144` |
| 遗留死代码 | `rg` 无其他模块 import `config.py` / `storage.py` / `douyin_bot.py` |

> **两类证据必须分开标注**：运行验证能证明「代码确实这样运行」，
> 静态审查只能证明「代码这样写」。混在一起会让审计的可信度被高估。

## AC-0.3 许可证边界明确

| 项 | 内容 |
|---|---|
| 条件 | 新项目对 **`douyin-bot` 与 `douyin-robot` 两个仓库均采用独立实现**，不复制任何代码 |
| 证据 | ① 确认 `douyin-robot` 无 LICENSE、`douyin-bot` 为 MIT；② 决策记录中明确写出「两个都独立实现」（D-001）；③ 新项目文件不复制两边的注释与函数体 |
| 失败状态 | 停止开发，先解决授权 |
| 类型 | 人工检查 |

> **为什么 MIT 的项目也不复制**：MIT **允许**复制（需保留声明），但本项目选择**不复制**，
> 因为两个参考项目的实现都带有已识别缺陷（见 SOURCE_AUDIT），复制会把缺陷一起带进来。
>
> 「法律上允许」与「工程上应该」是两件事。本项目的选择是：**两个都只借鉴设计**。
> 若未来确实需要复用 `douyin-bot` 的某段代码，须单独记录决策并保留 MIT 声明。

## AC-0.4 平台授权状态与运行模式分离记录

| 项 | 内容 |
|---|---|
| 条件 | **授权状态**（`unknown` / `go` / `no-go`）与**运行模式**（L0/L1/L2/L3）分别记录，且运行模式不超出授权状态允许的上限 |
| 证据 | ① `docs/DECISIONS.md` 中有独立的授权状态条目，含来源 URL、核查日期、适用范围、结论；② 运行模式条目**引用**授权状态并说明推导关系；③ 授权为 `unknown` 或 `no-go` 时，运行模式必须为 **L3** |
| 失败状态 | 未决 → 强制 L3；任何 L1/L2 的自动读取都视为**违反 AC** |
| 类型 | 证据记录 |

> **修正说明**：初版写「未决 → 一律按 L1 执行」，这是错的。
> L1 和 L2 **都包含对真实平台的自动读取**。授权未决时「降级到 L1」并不能让它变合规。
>
> 正确的推导链：
> ```
> 授权 unknown/no-go → 只能 L3（本地模拟，不接触真实账号）
> 授权 go           → 可选 L1（默认）或 L2；L0 需额外决策
> ```
>
> **这一条不通过，阶段 3 的真实平台适配器不得开始。**
> 阶段 1（CLI 骨架）与阶段 2（SQLite 归档）使用 mock 数据，不受影响。

## AC-1.1 启动自检可用

| 证据 | ① 在**缺少配置**的干净目录运行 `doctor --json`，输出九项结果及修复建议，退出码非 0；② 把数据目录设为 `chmod 555` 的已存在目录 → D5 报 `FAIL` 且含路径；③ 目录不存在但父目录可写 → D5 报 `OK`（能创建） |

## AC-1.2 配置缺失必须报错，不得静默兜底

| 项 | 内容 |
|---|---|
| 条件 | **配置结构**缺少必需字段时，加载失败并指出具体字段路径；但「目标账号未填写」属于**运行条件缺失**，不影响 `doctor` / `status` / `logs` 等只读命令 |
| 证据 | ① 删除 `runtime.cycle_seconds` → 输出包含 `runtime.cycle_seconds` 与缺失说明；② 保留 `target.douyin_id` 为空 → `doctor` 仍能跑完并输出 `WARN: 目标账号未配置`；③ `run` 在此状态下拒绝启动并指向该字段 |
| 失败状态 | 结构缺失 → 拒绝加载；运行条件缺失 → 允许只读命令，拒绝 `run` |
| 类型 | 自动测试 |

> 对应 SOURCE_AUDIT §2.2：`douyin-robot` 因 `.get(key, 默认值)` 导致轮询间隔静默取到 1 秒。
> **配置校验（结构是否合法）与运行条件（能否真正执行）必须分开**：阶段 1 不应因为目标账号未填就阻止 CLI 自检。

## AC-1.3 无标准库同名模块

| 项 | 内容 |
|---|---|
| 条件 | **`src/` 目录下**不存在与 Python 标准库同名的模块文件 |
| 证据 | ① 自动检查脚本遍历 `src/**.py`，与 `sys.stdlib_module_names` 求交集，结果为空；② 在 `src/` 下临时创建 `selectors.py` → D3 报 `FAIL`；③ 在 `douyin-robot/src/` 下存在 `selectors.py` → D3 **仍为 `OK`**（参考项目不在扫描范围） |
| 失败状态 | `doctor` 报错，CI 失败 |
| 类型 | 自动测试 |

> 证据③ 是关键的**反向断言**：仓库内有参考项目的同名文件（实测 `douyin-robot/src/selectors.py`）。
> 若扫描范围未限定，`doctor` 会永远报错。扫描规则见 CLI_SPEC §2.2 D3。

## AC-1.4 登录失效进入明确暂停状态

| 项 | 内容 |
|---|---|
| 条件 | 登录态失效时，进程进入 `paused_auth` 状态并**退出**（退出码 `3`），**不进入重试循环** |
| 证据 | **阶段 1**：注入故障（模拟检查函数返回「凭证失效」）→ 状态文件为 `paused_auth` → 进程退出码 `3` → 重启服务不会自动重试。**不连接真实抖音** |
| 失败状态 | 若进入重试、或以退出码 `4` 退出 → AC 失败 |
| 类型 | 自动测试 |

> 阶段 1 只验证「登录失效」这一**状态在状态机里存在且行为正确**，不验证「如何得知登录失效」。
> 后者依赖真实平台，属于阶段 3。

## AC-1.5 暂停与恢复

| 项 | 内容 |
|---|---|
| 条件 | `cli pause` 让运行中的实例在**当前轮结束后**进入 `paused_manual`（进程存活、可恢复）；`cli resume` **实际唤醒进程**并确认恢复为 `running` |
| 证据 | ① 启动 → `pause` → `status` 依次观察到 `pause_requested` → `paused_manual`；② 记录 `paused_manual` 时的 PID，`resume` 后断言**同一 PID 仍存活**（不是重启）；③ `resume` 返回 `0` 且 `status` 为 `running`；④ 挂起期间进程 CPU 占用可忽略（每 2 秒一次 stat） |
| 失败状态 | 若 pause 直接杀掉进程、状态无法区分「暂停」与「已停止」、或 resume 只改状态文件而进程仍挂起 → AC 失败 |
| 类型 | 自动测试 |

> 状态语义见 ARCHITECTURE §8：`paused_manual` 与 `stopped` 必须是**不同状态**。
> 前者表示「进程还在、等待恢复」，后者表示「进程已退出」。
>
> **证据 ② 是核心**：只断言「状态字段变成 running」无法区分「进程真的醒了」和「只是文件被改了」。
> 必须断言 PID 不变且存活，才能证明是恢复而非重启。

## AC-1.5b `resume` 超时必须报错

| 项 | 内容 |
|---|---|
| 条件 | 挂起进程无响应时，`resume` 在 `3 × pause_poll_seconds` 后超时，返回退出码 `4` 并给出可操作提示，**不自行 kill 进程** |
| 证据 | 冻结挂起进程（`SIGSTOP`）→ 执行 `resume` → 断言退出码 `4`、输出含「进程未响应」与「dac stop 后重新 dac run」；断言进程仍存活 |
| 失败状态 | 若 `resume` 无限等待、或静默返回 `0` → AC 失败 |
| 类型 | 自动测试 |

## AC-1.5c 控制意图幂等

| 项 | 内容 |
|---|---|
| 条件 | 同一个 `request_id` 只被消费一次；重复写入不会导致状态抖动 |
| 证据 | 连续写入两次相同 `request_id` 的 resume → 断言只发生一次状态转换 |
| 失败状态 | AC 失败 |
| 类型 | 自动测试 |

## AC-1.6 单实例保护

| 项 | 内容 |
|---|---|
| 条件 | 同一数据目录不允许启动第二个实例 |
| 证据 | 启动两次，第二次明确报错并退出，退出码可区分 |
| 失败状态 | 若两个实例同时写库 → 严重缺陷 |
| 类型 | 自动测试 |

## AC-1.7 退出码语义

| 项 | 内容 |
|---|---|
| 条件 | 退出码语义与 CLI_SPEC §8 一致：`0` 正常/意图达成、`1` 不可恢复、`2` 调用前置条件不满足、`3` 需要人工介入、`4` 可重试 |
| 证据 | ① 构造五种场景各断言退出码；② **`stop` 在 PID 已死时返回 `0`**；③ **`pause` 在 `stopped` 状态返回 `2`**；④ 状态文件不存在时 `status` 返回 `0` 而非 `2` |
| 失败状态 | 不进入阶段 7（systemd 无法正确决策） |
| 类型 | 自动测试 |

> 证据②③④ 覆盖三种最容易做错的情况：
> 「意图已达成不应报错」「前置条件不满足不应伪装成功」「正常初始状态不是错误」。

## AC-2.8 无法对齐时不得静默丢弃

| 项 | 内容 |
|---|---|
| 条件 | 本次读取结果与已有归档**完全无重叠**时，按 Contract 规定的方式处理，**原始输入必须保留**（写入待确认区或标记 `gap`），且结果确定 |
| 证据 | ① 构造无重叠输入 → 结果符合 Contract 描述；② 断言原始消息**仍可从库中查到**（无论在正式表还是待确认表）；③ 连续两次相同输入 → 结果一致 |
| 失败状态 | 若行为不确定、或原始数据丢失 → AC 失败 |
| 类型 | 自动测试 |

> **这一条需要先定 Contract。** 策略在阶段 2 启动时决定并记录理由。
>
> **注意**：初版写「三选一（追加/标记 gap/拒绝）」，但「拒绝」意味着丢弃输入。
> 修正后：**任何策略都不允许静默丢弃原始数据**（ARCHITECTURE §5.2）。

## AC-2.8b 歧义结果必须显式表达

| 项 | 内容 |
|---|---|
| 条件 | `no_id_mode` 下，当现有信息不足以判断一条消息是新事件还是重复出现时，归档结果为 `ambiguous`，**不得**猜测性地归入 `new` 或 `matched` |
| 证据 | 构造「两条内容相同、位置信息不足」的输入 → 断言结果为 `ambiguous`；断言该条不参与去重判定、不触发后续处理 |
| 失败状态 | 若静默归为 `new`（可能重复入库）或 `matched`（可能丢消息）→ AC 失败 |
| 类型 | 自动测试 |

> 这是对初版「不重复、不丢失」绝对保证的替代：
> **无法保证时，必须诚实地报告不确定**（ARCHITECTURE §5.2）。

# 每个 Slice 的固定四问

开发任何一个 Slice 前，必须先回答并记录：

1. **这一轮究竟要完成什么？**（对应哪几条 AC）
2. **什么证据能够证明完成？**（具体命令与预期输出）
3. **失败时系统会处于什么状态？**（必须是明确状态，不能是「崩溃」）
4. **能否解释从输入到结果的完整执行链？**（Understanding Gate）

> 第 4 问不通过 → 该 Slice 不算完成，即使测试通过。
