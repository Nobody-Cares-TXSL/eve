# 验收条件 — AC

> 版本：v1.1
> 状态：阶段 0 交付物
> 范围：**仅阶段 0～2**。阶段 3 之后的 AC 在对应阶段启动前定义，不提前写。
> 规则：AC 一经确认，不得为了通过测试而修改。发现不合理必须先记录变更原因。

---

## 使用方式

每条 AC 包含四个字段：

- **条件**：可观察的期望行为
- **证据**：什么能证明它成立（必须是可重复执行的）
- **失败状态**：不满足时系统处于什么状态
- **类型**：`自动测试` / `人工检查` / `证据记录`

「证据」不能是「看起来正常」，必须是命令输出、测试结果或文件。

# 阶段 1：最小 CLI 与基础可靠性

## AC-1.1 启动自检可用

| 项 | 内容 |
|---|---|
| 条件 | `cli doctor` 能检查并逐项报告：Python 版本、依赖是否安装、配置是否存在、配置是否合法、凭证是否存在、目录权限 |
| 证据 | 在**缺少配置**的干净目录运行 `cli doctor`，输出每一项的 `OK` / `FAIL` 及修复建议，退出码非 0 |
| 失败状态 | 不进入阶段 2 |
| 类型 | 自动测试 |

## AC-1.2 配置缺失必须报错，不得静默兜底

| 项 | 内容 |
|---|---|
| 条件 | **配置结构**缺少必需字段时，加载失败并指出具体字段路径；但「目标账号未填写」属于**运行条件缺失**，不影响 `doctor` / `status` / `logs` 等只读命令 |
| 证据 | ① 删除 `runtime.cycle_seconds` → 输出包含 `runtime.cycle_seconds` 与缺失说明；② 保留 `target.douyin_id` 为空 → `doctor` 仍能跑完并输出 `WARN: 目标账号未配置`；③ `run` 在此状态下拒绝启动并指向该字段 |
| 失败状态 | 结构缺失 → 拒绝加载；运行条件缺失 → 允许只读命令，拒绝 `run` |
| 类型 | 自动测试 |

> 对应 SOURCE_AUDIT §2.2：`douyin-robot` 因 `.get(key, 默认值)` 导致轮询间隔静默取到 1 秒。
> **配置校验（结构是否合法）与运行条件（能否真正执行）必须分开**：阶段 1 不应因为目标账号未填就阻止 CLI 自检。

## AC-1.3 无标准库同名模块

| 项 | 内容 |
|---|---|
| 条件 | 项目中不存在与 Python 标准库同名的模块文件 |
| 证据 | 自动检查脚本：遍历项目 `.py` 文件名，与 `sys.stdlib_module_names` 求交集，结果为空 |
| 失败状态 | `doctor` 报错，CI 失败 |
| 类型 | 自动测试 |

## AC-1.4 登录失效进入明确暂停状态

| 项 | 内容 |
|---|---|
| 条件 | 登录态失效时，进程进入 `paused_auth` 状态并**退出**（退出码 `3`），**不进入重试循环** |
| 证据 | **阶段 1**：注入故障（模拟检查函数返回「凭证失效」）→ 状态文件为 `paused_auth` → 进程退出码 `3` → 重启服务不会自动重试。**不连接真实抖音** |
| 失败状态 | 若进入重试、或以退出码 `4` 退出 → AC 失败 |
| 类型 | 自动测试 |

> 阶段 1 只验证「登录失效」这一**状态在状态机里存在且行为正确**，不验证「如何得知登录失效」。
> 后者依赖真实平台，属于阶段 3。

## AC-1.5 暂停与恢复

| 项 | 内容 |
|---|---|
| 条件 | `cli pause` 让运行中的实例在**当前轮结束后**进入 `paused_manual`（进程存活、可恢复）；`cli resume` **实际唤醒进程**并确认恢复为 `running` |
| 证据 | ① 启动 → `pause` → `status` 依次观察到 `pause_requested` → `paused_manual`；② 记录 `paused_manual` 时的 PID，`resume` 后断言**同一 PID 仍存活**（不是重启）；③ `resume` 返回 `0` 且 `status` 为 `running`；④ 挂起期间进程 CPU 占用可忽略（每 2 秒一次 stat） |
| 失败状态 | 若 pause 直接杀掉进程、状态无法区分「暂停」与「已停止」、或 resume 只改状态文件而进程仍挂起 → AC 失败 |
| 类型 | 自动测试 |

> 状态语义见 ARCHITECTURE §8：`paused_manual` 与 `stopped` 必须是**不同状态**。
> 前者表示「进程还在、等待恢复」，后者表示「进程已退出」。
>
> **证据 ② 是核心**：只断言「状态字段变成 running」无法区分「进程真的醒了」和「只是文件被改了」。
> 必须断言 PID 不变且存活，才能证明是恢复而非重启。

## AC-1.5b `resume` 超时必须报错

| 项 | 内容 |
|---|---|
| 条件 | 挂起进程无响应时，`resume` 在 `3 × pause_poll_seconds` 后超时，返回退出码 `4` 并给出可操作提示，**不自行 kill 进程** |
| 证据 | 冻结挂起进程（`SIGSTOP`）→ 执行 `resume` → 断言退出码 `4`、输出含「进程未响应」与「dac stop 后重新 dac run」；断言进程仍存活 |
| 失败状态 | 若 `resume` 无限等待、或静默返回 `0` → AC 失败 |
| 类型 | 自动测试 |

## AC-1.5c 控制意图幂等

| 项 | 内容 |
|---|---|
| 条件 | 同一个 `request_id` 只被消费一次；重复写入不会导致状态抖动 |
| 证据 | 连续写入两次相同 `request_id` 的 resume → 断言只发生一次状态转换 |
| 失败状态 | AC 失败 |
| 类型 | 自动测试 |

## AC-1.6 单实例保护

| 项 | 内容 |
|---|---|
| 条件 | 同一数据目录不允许启动第二个实例 |
| 证据 | 启动两次，第二次明确报错并退出，退出码可区分 |
| 失败状态 | 若两个实例同时写库 → 严重缺陷 |
| 类型 | 自动测试 |

## AC-1.7 退出码语义

| 项 | 内容 |
|---|---|
| 条件 | 退出码区分：`0` 正常、`2` 配置错误、`3` 需要人工介入、`4` 可重试错误 |
| 证据 | 构造四种场景，分别断言退出码 |
| 失败状态 | 不进入阶段 7（systemd 无法正确决策） |
| 类型 | 自动测试 |

| 证据 | ① 空目录启动 → 表存在；② 写入数据 → 再次启动 → 数据仍在 |

## AC-2.2 归档确定性

| 项 | 内容 |

## AC-2.8 无法对齐时的确定性处理

| 项 | 内容 |

# 每个 Slice 的固定四问

开发任何一个 Slice 前，必须先回答并记录：

1. **这一轮究竟要完成什么？**（对应哪几条 AC）
2. **什么证据能够证明完成？**（具体命令与预期输出）
3. **失败时系统会处于什么状态？**（必须是明确状态，不能是「崩溃」）
4. **能否解释从输入到结果的完整执行链？**（Understanding Gate）

> 第 4 问不通过 → 该 Slice 不算完成，即使测试通过。
